# 全链路索引对照

从真实 HTTP 请求开始，经过用户画像读取、定向及一价竞价、预算/频控预占、曝光/点击/转化回传、MySQL 事务提交、Redis 曝光结算、Outbox 投递、Kafka 消费，最终核对 MySQL 统计及 Redis 资金/频控状态。

不把 HTTP 202 当成异步处理完成，不把 SQL 微基准提速倍数推广为接口提速。

## 环境与运行

当前入口为本项目的 Linux/WSL 原生环境：

- root 可通过 `/var/run/mysqld/mysqld.sock` 认证 MySQL。
- `redis-server` 在 PATH 中；脚本创建自己独占的、无持久化的 Redis 子进程并使用随机本机端口，不碰业务 Redis。
- Kafka 为 `127.0.0.1:9092`；CLI 位于 `/opt/adflow-runtime/kafka_2.13-4.3.1/bin`，需允许创建/删除测试 Topic 和消费组。
- 数据库、Redis、Kafka 与 API 共享本机硬件资源。本实验是正确性与有界负载对照，不是生产容量验收。

在 Windows 仓库根目录的独立 PowerShell 中：

```powershell
New-Item -ItemType Directory -Force work/end-to-end | Out-Null
$env:GOOS = 'linux'
$env:GOARCH = 'amd64'
go build -o work/end-to-end/api-linux ./cmd/api
go build -o work/end-to-end/full-chain-linux ./tests/bench/full-chain
wsl.exe -d Ubuntu -u root -- bash -lc 'cd /mnt/d/AdFlow && ./work/end-to-end/full-chain-linux -output work/end-to-end/run-01'
```

输出目录必须尚不存在，脚本拒绝覆盖。Linux 下可直接编译执行；务必在仓库根目录运行，以便读取迁移和记录源码摘要。

默认参数：`-rows 1000000 -requests 120 -rounds 3 -rate 10`。小规模检查：`-rows 1000 -requests 10 -rounds 1 -rate 5`。每个场景执行三轮配对，模式顺序为 AB、BA、AB；A 为目标索引不可见，B 为可见。两个场景共 12 组正式运行。

## 固定工作负载

- 原封不动运行 `cmd/api` 编译出的程序，启用 JWT、MySQL 审计、MySQL 存储、Redis 画像缓存/限流/预占和 Kafka 事件链路。
- API 每组重新启动以对齐进程内状态；决策超时 1s、画像缓存超时 50ms，其他参数按当前默认值，不在模式间改变。
- 每组通过 HTTP 创建 3 个广告计划与素材，同一广告位、相同定向条件、3 个广告主分别出价 2/3/5 分。创建真实已保存用户并预热画像缓存。
- 先跑 3 次完整预热流程，等待统计落库。预热不计入耗时分位数，但纳入每组金额和事件数量核验。
- 正式请求按 10 轮/秒派发，最多 20 个客户端在途流程，每轮一次决策、顺序发送曝光/点击/转化。转化价值固定 500 分，每次曝光应按 5 分结算。
- 所有用户都应真实命中最高出价计划。No-Ad 属于本工作负载的异常，不用于稀释耗时或错误率。
- 每组使用独立广告计划、用户与请求 ID；历史测量数据保留，进入下一组前验证本组已全部处理。最终新增业务事件总量远小于百万历史行，但不是每组恢复完全相同数据库快照，报告应说明这点。

## 两种背景

1. **healthy_history**：百万条合成历史事件全部为 PUBLISHED。验证正常队列下，单条 SQL 的巨大收益是否真的体现在全链路上。
2. **stranded_backlog**：将约 5% 历史事件改为 SETTLING，且不建立其结算任务。这是明确构造的**静态滞留压力夹具**，只用于维持扫描压力；不冒充健康生产队列或可自行排空的真实积压。

历史夹具 ID 使用 `hist-` 前缀，测量用 `e2e-`，最终核账只针对本组请求，不要求压力夹具全部处理完成。保留原有队列索引，只切换 `(aggregate_key,status)` 的可见性；索引不可见仍存在维护成本。

## 三个时间口径

- `decisionMs`：一次决策 HTTP 请求从发送至完整读回响应。
- `allEventsAcceptedMs`：从决策开始，到曝光、点击和转化均收到成功响应，包含真实入口事务提交，但异步结算/计量未必完成。
- **`committedObservedMs`**：从决策开始，到并行观察器首次查到该请求的三个已提交 `processed_events` 行。消费端在同一事务中写去重记录和更新统计，因此这代表该组事件已完成消费及统计事务提交。包含 100ms 轮询间隔及查询/调度开销，是观察到完成的时间上界，不是精确提交时刻。

另外保存 `allEventsProcessedMs` 和 `lastProcessedAt`，来自数据库记录内的时间戳。这个字段在事务提交前赋值，只作诊断，**不能当成精确提交耗时**。观察器在正式派发开始时并行启动，而不是等全组派发完才开始统计。

## 每组核验

- 120 个正式请求 + 3 个预热：应有 123 次成功结算、369 条事件受理/发布/消费。
- 最高出价计划应计入 123 次曝光、123 次点击、123 次转化；模拟转化价值 61,500 分，预算扣费 615 分，未结预占 0。
- 每个独立用户频控计数为 1，其他广告主没有获得统计。
- 完成后重复提交一份决策及三类相同事件，事件返回 `recorded=false`，账目与计数不增加。
- 查看一条真实请求的处理过程，检查三分区 Kafka lag 快照为 0，并保存该组 Outbox 状态计数。
- 出错时保留原始样本、错误和日志，不通过自动重试掩盖失败请求。正确性失败会使最终命令非零退出。

## 隔离与留档

实验只创建 `adflow_e2ebench_*` 新库，应用全部迁移，不读取业务 `.env`，不调用付费模型。启动自己持有的 API/Redis 进程和专用 Kafka Topic/消费组。结束时停止这些进程、删除生成的库和 Topic/消费组，清理结果写入报告。

原始 JSON 保存每轮分位数、每个请求的状态码和时间、资金/事件核验、请求追踪例子、环境和源码/二进制摘要。API/Redis 日志在指定输出目录。脚本会清理隔离库，即使失败也应先从日志和报告排查，不依赖残留数据库。

独立统计复核与跨轮汇总：

```sh
python tests/bench/full-chain/verify.py path/to/results.json
```

统计时从逐次样本重新合并计算分位数，不能平均三个 P95。没有进行断网、进程崩溃、主从切换或最大容量探索，不把这些写成此次验收成果。
