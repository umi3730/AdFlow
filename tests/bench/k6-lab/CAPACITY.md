# Kafka 全业务链路容量

验证异步积压保护使用独立模式：`run-k6-walkthrough.ps1 -Backpressure -ConfirmSeconds 120`。依次跑 45 次/秒正常负载、100 次/秒过载和 45 次/秒恢复，单独记录明确的 503 拒绝并核对所有已受理事件。此模式不产生最大容量结论；普通 Capacity 模式仍将拒绝作为未达到目标负载处理。

```powershell
cd D:\AdFlow
.\tests\load\run-k6-walkthrough.ps1 -Capacity -Seconds 20 -ConfirmSeconds 60
```

只针对某一档位做三轮确认：

```powershell
.\tests\load\run-k6-walkthrough.ps1 -Capacity -CapacityRate 50 -ConfirmSeconds 60
```

复用原有隔离环境管理：新 MySQL 库、独占 Redis 进程、专用三分区 Kafka Topic/消费组、真实 API。不会修改业务数据、连接池、worker 或 relay 配置。所有资源结束后清理，原始报告保留在命令打印的 work 目录。

## 负载

一轮包含 1 次决策和曝光/点击/转化各 1 次回传，所以 R 轮/秒约对应 4R HTTP 请求/秒、3R Kafka 事件/秒。固定到达率由真实 k6 v2.2.0 产生，不是 Go 工具模拟数字。

1000 个已保存用户、每阶段新建 3 个广告主计划（2/3/5 分出价），全部满足定向，必须命中 5 分计划。每阶段 3 次完整预热流程不计入正式速率和分位数，但计入该计划的预算/统计核验。画像重新预热，只删除独占 Redis 中这些画像的值键，不清空预算或结算凭据。

每阶段使用独立计划和请求前缀，保留之前的决策与事件。日预算足够，频控上限保持 100；预占、实际曝光扣费和幂等均启用。

## 搜索标准

初始阶梯 10/25/50/75/100/150/200/300/450 轮/秒，短测默认 20 秒，遇到失败后以 5 轮/秒分辨率缩小区间。候选速率需 3 次较长确认（默认各 60 秒），失败则回退 5 轮/秒，最多 6 级。

每阶段同时要求：

- 决策 P95 < 300ms。
- 决策到三类事件均受理的 P95 < 1000ms。
- 决策到三类事件统计提交可见的 P95 < 5000ms。
- 业务错误率 < 0.1%，无 No-Ad，无 dropped iterations，实际派发不低于计划的 99%。
- 结束后 10 秒内排空；所有受理事件的结算、Outbox 发布、消费与统计金额一致，预占余额为 0。
- 三个 Kafka 分区的 broker 消费组 lag 为 0，重复回传不重复记账。

若搜索达到预定上界仍未失败，只能报告验证的下界。如果没有任何候选通过长期确认，也明确保留该结论，不修改阈值。

## 观测与核账

requestId 携带客户端开始的 Unix 毫秒值和迭代序号。Go 观察器在负载运行时每 250ms 查询当前阶段的消费记录，首次看到同一请求的 3 条已提交记录时记录完成延迟。消费记录与统计在同一事务写入。

这项完成时间含轮询、查询和调度开销，使用同一 WSL 主机时钟；记录内的 processed_at 在提交前赋值，另存作诊断，不能替代实际提交观测。观察器本身增加数据库读负载，这也是本次测试条件的一部分。

每秒保存决策/受理/结算/发布/消费计数，观察积压。测试后核对每个事件类型的计数、5 分曝光扣费、500 分转化价值；重复回传一组已处理事件，检查 recorded=false 和账目未增加。保存 Kafka broker 的消费组偏移输出。

有限时长 SLO 通过不代表队列长期稳定。额外用 `queue_trend.py` 排除前 5 秒，比较派发期间最初/最后 5 个采样的平均未消费数；增长超过一批（100 条）作为积压增长警示，避免把停发后排空误称为持续不积压。这个辅助观察也不能证明无限时长稳定。

出现 RECONCILE 时排空观察会提前退出，此时 `drainAfterLoadSeconds` 只表示退出前的观察耗时，不表示队列排空。完成样本不全时，已完成子集的 P95 不能代表全部请求；`verify_capacity.py` 的全量 P95 输出为 null，`queue_trend.py` 将该阶段列入 excludedStages，避免用子集起止时间推断整段派发窗口。

预热未排空等中止阶段可能没有正式 k6 结果。核验工具将其单列 incompleteStages，不计为正式确认通过。`verified=true` 只表示完整记录的计算核验通过，不能替代每阶段的 passed/accountingPassed。过载残留导致下一档预热中止后，应使用 `-CapacityRate` 另开独立环境确认。

此测试不做断网、崩溃或副本切换，Kafka 使用本地三分区、单副本。它证明当前本机链路在指定时间和 SLO 下的表现，不代表 Kafka 本身的吞吐上限或生产服务容量。
