# 核心审查四项修复（2026-09-07）

对应 `core-correctness-review-20260907.md` 中四项发现。本机 18080、18081 均已更新，MySQL 迁移到 `000012_profile_identity`。

## 1. 用户 ID 语义

用户画像 ID 定义为区分大小写、区分重音的标识；首尾空白与决策入口保持一致，会被去除。例如 `user-a` 与 `USER-A` 是不同 ID。只创建前者时，后者查不到画像；明确创建后者才会新增另一位用户，不会修改前者。

- user_profiles.user_id 改为 MySQL 8 的 utf8mb4_0900_bin，消除大小写、重音及 PAD SPACE 比较导致的别名。
- 内存、MySQL、缓存的读写删除与画像构造统一处理首尾空白，空 ID 不允许保存。
- 缓存协议命名空间升到 g3，避免升级后继续读取旧排序规则下产生的别名缓存；没有清空预算、频控或整个 Redis。
- 页面与 OpenAPI 补充大小写说明。

迁移前检查了首尾空白归一化冲突和空 ID，本机均为零；数据库已备份到忽略目录 `work/core-review/before-fix-migration.sql`。迁移不合并用户；空白处理若产生唯一键冲突会失败。回滚到旧排序规则时，若已创建大小写不同的新 ID，也会因冲突失败，需要先核对数据。

原审阅夹具按“数据库只有一个不区分大小写的用户”断言；新契约明确区分两个 ID，所以正式回归验证的是：未创建的别名不能获得画像/频控额度，显式创建另一个 ID 后，两份数据各自独立，更新、删除与缓存结果一致。

## 2. 同步事件幂等与结算

同步入口使用回执存储协议，先登记 eventId、requestId、事件载荷、决策快照及首次受理时间，然后原子结算预算与频控，最后提交指标。

- 相同 eventId 参数冲突返回 event_conflict，不再确认另一个请求的预留。
- 同一 requestId 只允许一个曝光 eventId，换事件 ID 不能重复计量。
- 重试使用首次回执和成交快照，不使用重试时间覆盖原事件。
- 结算失败前不增加指标；Redis 已确认但响应丢失时，重试可复用幂等凭证，原曝光有效期已过也不会重复扣费。
- 32 个并发重复回传只产生一次指标提交、一次 5 分结算。
- 全局内存锁只用于短暂登记和提交，Redis 调用在锁外执行。

同步回执和指标仍是进程内状态，适用于本地同步演示；跨进程持久恢复继续使用 Kafka 模式。同步混用 Redis 时，网络不确定错误需要按原 eventId 重试，不能据此宣称内存指标具有崩溃恢复能力。

## 3. 拆分曝光有效期与行为归因

- 新曝光仍需在原决策有效期内回传，默认预留期保持 30 秒；不会放开过期曝光扣费。
- 点击与转化依据原曝光回执的请求、计划、素材及服务器受理时间验证，目前统一采用七天归因窗口，不再依赖原决策仍然有效或仍在内存中。
- 没有原曝光、身份不匹配、事件时间早于曝光，或超过归因窗口的新事件会被拒绝。
- 已受理事件的相同重试在窗口结束后仍返回原受理结果。
- 消费端只对曝光继续检查原曝光有效期；点击/转化以入口已经验证、且通过持久化载荷证明的事件为准，允许消息延迟消费，不把重放时间当作新的归因时间。

异步模式可以先受理曝光的后续行为，结算未完成时这些事件仍等待，不能提前计量。同步模式只有结算并计量成功的曝光才能作为后续行为依据。

## 4. 测试资源清理

修正了结算恢复与画像代次测试中 defer Close 先于 t.Cleanup 删除键的问题。客户端关闭改为按清理顺序注册；deletePrefix 返回扫描/删除错误，调用方将错误报告为测试失败。增加空前缀保护、清理超时以及父测试核验子测试结束后键已消失的回归。

本轮新建的真实归因测试使用同一 defer 顺序完成“删除数据 → 关闭 Redis → 关闭数据库”，未复制原先的生命周期问题。
