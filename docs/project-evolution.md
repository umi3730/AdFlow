## V1：基础投放版

### 目标与实现

先完成一次投放所需的业务流程：创建计划与素材、准备用户画像、匹配定向、检查预算和频控、返回广告，再接收曝光、点击和转化，更新统计。

- 使用 Go/Gin 构建模块化单体，按领域、应用服务和适配器组织代码。
- 完成计划创建、发布、暂停、恢复以及素材启停，发布规则保存为不可变快照。
- 支持标签与字段的 ALL/ANY/NONE 定向规则。
- 实现固定成本投放、预算和频控预占、事件回传与基础计量。
- 提供内存适配器和 MySQL/Redis/Kafka 接入，配套管理台、JWT/RBAC 和操作审计。

这一阶段形成后续优化共用的业务模型、接口和测试入口。

**面试讲法：**“我先把广告投放拆成计划、决策、事件三个核心模块，跑通从规则配置到投放统计的闭环，再通过适配器接入数据库、缓存和消息队列。”

参考：[功能说明](getting-started.md)、[计划领域模型](../internal/campaign/domain/campaign.go)、[决策服务](../internal/decision/application/service.go)。历史实现入口：`222a670`（基础平台）、`232b2ae`（权限与审计）、`ca50d13`（规则编辑与确认发布）。

## V2：吞吐优化版

### 优化动机

接入真实依赖后，压测暴露了候选读取的 N+1 查询、重复读取配置与画像，以及事件逐条处理带来的数据库和网络开销。

### 主要改动与结果

| 原先的问题 | 实施的优化 | 对应成果 |
| --- | --- | --- |
| 每次决策先查询计划，再逐个查询素材 | 按广告位过滤候选，批量读取素材 | 20 个计划场景下，候选读取由 21 次 SQL 减至 2 次 |
| Kafka 各分区串行、逐条提交与写库 | 分区间并行、分区内有序；批量查询、事件落库、统计更新和偏移提交 | 减少逐条操作的往返与事务开销 |
| 同一广告位的配置反复查询 | 按广告位缓存候选快照，并合并并发刷新 | 多个请求复用配置读取结果 |
| 同一用户画像重复回源 | Redis Cache-Aside、负缓存、并发回源合并 | 热画像请求直接读取缓存 |

早期“决策＋曝光”基准的演进记录：

| 阶段 | 通过的负载档位 |
| --- | ---: |
| 去除 N+1 后的真实依赖基线 | 20 轮/秒 |
| 批量事件处理 | 50 轮/秒 |
| 候选快照缓存 | 80 轮/秒 |
| 画像 Cache-Aside | 100 轮/秒 |

这组数据用于讲述当时同一类负载的逐步优化。后续竞价、持久化结算及三类事件齐全的容量实验单独记录。

**面试讲法：**“我先从 SQL 次数入手定位 N+1，再优化事件批处理；对于低频变化的候选配置和重复访问的画像，分别加入缓存和并发回源合并，逐步减少每次请求需要做的数据库工作。”

参考：[性能基线与逐步对照](performance-baseline.md)、[候选快照](../internal/decision/adapter/campaign/cached_provider.go)、[Kafka 消费](../internal/event/adapter/kafka/client.go)。历史提交：`4ab99b3`（查询优化）、`3fec011`（批处理）、`dfbe643`（候选缓存）、`38db044`（画像缓存）。

## V3：竞价与可靠结算版

### 优化动机

增加多广告主竞价后，系统需要保存真实成交结果，并解决并发重复执行、跨存储结算失败、消息重复投递及 worker 中断后的恢复问题。

### 主要改动

- 实现内部一价竞价，保存获胜广告主、计划版本和整数分成交价，后续结算使用原成交快照。
- 将请求参数指纹、执行权和预占所有权关联，避免重复执行及错误释放其他执行者的资源。
- 持久化曝光结算任务，通过 Redis Lua 同时确认预算和频控，并保存可重试的结算凭据。
- 结算完成后释放 Outbox 事件；消费端幂等处理，新增事件和统计在同一事务提交。
- 为已明确回滚的死锁/锁等待超时增加有界事务重试，完善 owner 校验和未完成任务归还。
- 增加 `(aggregate_key, status)` 联合索引，优化按请求释放待投递事件的 SQL。
- 为画像失效与回填引入 generation 校验，防止旧查询重新填入过期值。

### 适合展开的故障案例

一次压测中，MySQL 死锁使 worker 在批处理中途退出，剩余任务仍持有 30 秒租约。其他 worker 等到接管时，Redis 中同样只有 30 秒的预占已经过期，任务进入待核对。

处理方式：明确回滚后重试整笔事务；退出时按 owner 条件归还未完成任务；每批缩小到 4 条、租约缩短到 15 秒，并限制单次处理时间。恢复时复用 Redis 结算凭据，避免重复扣费。

对应验证包括真实 MySQL 死锁、MySQL/Redis 任务接管以及 Kafka 完整链路复测。数据库优化方面，百万条合成 Outbox 记录的索引对照将单条 UPDATE 服务端 P95 从 **164.52ms 降至 1.09ms**。

**面试讲法：**“这一阶段重点解决失败后的恢复。我遇到过死锁导致批次剩余任务被租约占住的问题，最终把事务重试、任务归还和结算凭据结合起来，让其他 worker 可以继续处理，同时避免重复扣费。”

参考：[竞价设计](auction-design-20260907.md)、[请求执行修复](decision-execution-fix-20260907.md)、[结算恢复](settlement-recovery-fix-20260908.md)、[索引对照](sql-index-experiment-20260908.md)、[画像缓存一致性](onboarding-cache-improvements-20260907.md)。相关阶段的集中提交为 `e941b34`，更细的实现及验证过程保存在上述文档中。

## V4：稳定性治理版

### 优化动机

HTTP 请求处理结束后，结算和发布任务仍在后台运行。只限制入口速率和同时执行的决策数，无法反映异步队列已经积累了多少工作。持续积压还可能消耗预占的有效时间。

### 主要改动与验证

- 将入口限流、执行并发限制、排队超时和请求期限组合起来，限制单实例正在执行的工作。
- 增加结算队列与 Outbox 高低水位背压：高水位暂停新决策，低水位恢复，已有事件继续处理。
- 用一个监控 goroutine 周期采样共享队列，请求读取原子快照；观测失效时暂停放行。
- 接入 Prometheus、按 requestId 联查、pprof 和数据库连接池统计，联合观察处理耗时、积压和数据库等待。
- 对最大连接数 30/60/100 做九组交叉实验，最终保留 30/10 默认配置，并继续记录空闲连接上限的对照线索。

过载验收采用“正常 → 过载 → 恢复”三个阶段：过载阶段每秒发起 100 次新决策尝试，受理 **6,681** 个完整流程、明确拒绝 **5,320** 次；已受理流程核账完成，回到 45 次/秒后恢复无拒绝处理。

该阶段也整理了容量基准：决策接口 **450 QPS、P95 100～103ms**；包含决策及曝光/点击/转化的完整链路 **45 轮/秒，三组各 120 秒**。容量、过载保护和调参对照分别用于回答不同问题。

**面试讲法：**“长测时我发现入口请求能成功，后台却会持续积压，所以增加了依据实际队列状态的背压。之后用正常、过载、恢复三个阶段验证，同时通过 pprof 和连接池统计定位下一步值得优化的地方。”

参考：[背压实现与验收](async-backpressure-20260908.md)、[决策容量](decision-capacity-20260908.md)、[完整链路容量](kafka-capacity-followup-20260908.md)、[最大连接数对照](mysql-pool-comparison-20260908.md)、[空闲连接对照记录](mysql-idle-pool-comparison-20260909.md)、[pprof 工具](profiling.md)。空闲连接对照仍有复测工作，当前里程碑只计入已经完成的观测和分析能力。

## V5：运营分析版

### 目标与实现

在投放和结算能力上增加分析入口，让用户查看效果、定位问题并形成调整建议。

- 新增独立 reporting 上下文，按北京时间小时/天聚合已处理事件，支持计划和时间筛选。
- 消耗取自已确认曝光的原成交快照，展示曝光、点击、转化、消耗、转化价值、CTR/CVR 和平均成本。
- 提供趋势图、明细分页、CSV 导出；汇总比率由总计数计算，补齐没有事件的时间段。
- 新增 Agent 投放诊断，结合服务端报表、当前计划/素材配置，以及可选请求的保存结果生成建议。
- 每条建议引用本次实际证据；复用 Go 模型调用层的结构化输出、重试、熔断和本地降级。
- 报表与诊断之间传递筛选条件，保留原有规则生成和人工确认发布流程。

实现经过 Go 回归与 vet、前端 122 项回归和生产构建，以及真实 MySQL 查询和完整 HTTP 联调验证。报表索引迁移 `000014` 已在本地数据库执行。

**面试讲法：**“最近我补了效果报表和 Agent 诊断。报表复用已去重事件与成交快照，Agent 再读取这些真实数据和请求结果，生成附带依据的调整建议，用户可以从报表直接进入诊断。”

参考：[报表与诊断实现](delivery-reports-and-diagnosis.md)、[报表查询](../internal/reporting/adapter/mysql/reader.go)、[诊断服务](../internal/agentassistant/application/diagnosis.go)、[报表索引迁移](../migrations/000014_delivery_reports.up.sql)。

## 一分钟项目介绍

> AdFlow 是我做的 Go 广告决策与投放验证项目，我把它的演进整理成五个阶段。第一阶段先完成计划配置、定向、预算频控和事件统计的业务闭环。第二阶段通过压测定位 N+1 和逐条处理的开销，加入批量查询、缓存以及 Kafka 批处理。第三阶段完善多广告主竞价和可靠结算，重点处理重复执行、死锁以及任务中断后的接管。第四阶段根据后台队列积压增加背压，并接入 pprof 和连接池监控做瓶颈分析。最近一版补了效果报表和 Agent 投放诊断。面试中我会重点展开查询优化、死锁后的结算恢复，以及异步积压保护这三个问题。

## 简历如何摘用

简历保留一个 AdFlow 项目，按自己的实际负责范围摘用以下四条；版本演进用于项目介绍和面试追问。

1. 基于 Go/Gin 构建广告决策平台，完成计划配置、用户定向、一价竞价、预算频控与事件统计，采用模块化单体和接口适配设计。
2. 通过批量查询消除候选读取 N+1，并结合候选快照、画像 Cache-Aside、并发回源合并和 Kafka 批处理降低读写开销。
3. 基于 Redis Lua、事务 Outbox 和持久化任务实现幂等结算；通过整事务有限重试、owner 校验和租约归还处理死锁后的恢复，并优化请求级 Outbox 联合索引。
4. 建立队列高低水位背压、Prometheus 与 pprof 观测，使用 k6 验证容量及过载恢复；扩展投放报表和基于服务端数据的 Agent 诊断。
