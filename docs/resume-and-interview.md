# AdFlow 简历与面试要点

适用于校招／实习 Go 后端。按实际参与范围选择“实现、参与、验证”等动词；以下是项目材料，不代表生产经历。Redis 集中写一条即可。

## 项目简介

**AdFlow 广告决策与投放验证平台｜Go、Gin、MySQL、Redis、Kafka、React**

面向广告投放模拟与验证，实现计划与素材管理、用户定向、一价竞价、预算频控、曝光结算及异步事件计量，提供请求追踪和效果报表。

## 简历正文（推荐版）

- 实现广告决策与事件处理链路，按请求标识保证决策幂等，保存规则版本和成交价快照；通过持久化结算队列、Transactional Outbox 与 Kafka 消费幂等衔接曝光扣费和统计落库。
- 使用 Redis Cache-Aside 缓存用户画像，结合负缓存、并发回源合并和代次校验处理缓存失效与旧数据回填；通过 Lua 脚本原子执行预算、频控预占，曝光后确认扣减。
- 针对按请求结算时扫描大量同状态记录的问题，采用 `(aggregate_key, status)` 联合索引；在百万行合成数据、6 轮索引可见性对照中，单条 UPDATE 服务端 P95 从 **164.52ms 降至 1.09ms**。
- 使用 k6 验证完整 Kafka 链路，在本机 **45 轮业务/秒、三组各 120 秒**下完成 **16202 个流程、48606 条事件**，统计提交可见 P95 **1.398s**；实现基于异步队列高低水位的准入保护，并验证过载拒绝与恢复。

篇幅紧张时保留其中三条。不要同时堆满接口 QPS、业务轮次、SQL 倍数和所有组件名；优先选择能解释清楚的工作。

## 用 STAR 讲一个具体优化

**S：** 曝光结算要按请求更新 Outbox 状态，历史事件增长后，原队列索引先定位同状态的大量事件，再筛选请求。

**T：** 验证请求维度联合索引能否减少扫描，并避免把单条 SQL 改善夸大为整个接口提速。

**A：** 使用同一物理表和相同数据，交替切换目标索引可见/不可见；每模式 UPDATE 采集 60 个样本，用执行计划和 Performance Schema 核对检查行数与服务端耗时，更新后回滚以保持可比。

**R：** 百万行场景下该 UPDATE 的服务端 P95 从 164.52ms 降至 1.09ms。该索引此前已在项目中，本次补的是独立验证；测试为单并发且不包含完整事务提交持久化，不能说生产接口快了同样倍数。

## 面试必须分清的数字

| 指标 | 含义与限制 |
| --- | --- |
| 画像查询 1000 QPS | 热缓存单接口，3×60 秒；不是整个系统容量。 |
| 决策接口 450 QPS | 3×60 秒、81003 次请求中有 2 次 HTTP 409；不发曝光/点击/转化。 |
| 完整链路 45 轮/秒 | 每轮 4 次 HTTP 调用、3 条事件，约 180 HTTP QPS；是本机该条件下通过的档位。 |
| 100 次新决策尝试/秒 | 12001 次尝试中完成 6681 轮、明确拒绝 5320 次；是过载保护验收，不能写成完成 100 轮/秒。 |
| 空闲连接 10/20 | 记录存在失败轮次和源码来源限制，不作为已落地的性能成果。 |

先讲业务完成标准，再讲吞吐。能追踪“受理→结算→发布→消费→统计”，比只说请求返回 200 更有说服力。
