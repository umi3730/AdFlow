# 广告决策接口：真实命中负载的稳定 QPS

## 结论

2026-09-08，使用 k6 对 **`POST /v1/decisions`** 进行阶梯加压和持续复测。当前本机条件下，最高通过三轮各 60 秒验收的测试档位为 **450 QPS**。

验收线在运行前固定：P95 < 300ms，HTTP 或业务错误率 < 0.1%，无未派发迭代、无 No-Ad、无错误竞价结果，持久化和预算预占核验通过。

| 450 QPS 确认轮次 | 实际 HTTP QPS | 请求数 | 正确命中数 | P95 | P99 | HTTP 异常 | 未派发 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 449.63 | 27,001 | 27,001 | 102.28ms | 252.05ms | 0 | 0 |
| 2 | 449.67 | 27,001 | 27,001 | 103.29ms | 248.73ms | 0 | 0 |
| 3 | 449.72 | 27,001 | 26,999 | 100.22ms | 292.58ms | 2 | 0 |

三轮共 **81,003 次请求，81,001 次成功命中，2 次 HTTP 409**，合并异常比例约 **0.00247%**。第三轮异常比例约 0.0074%，低于预设 0.1% 上限，所以按标准通过，但**不能写成零错误或所有请求成功**。

450 是以 25 QPS 分辨率、当前部署和负载验证的稳定档位，不是数学上的绝对最大值。475 QPS 的长测因为两次未派发未通过，450～475 未继续细分；结果不能直接外推到独立发压机或生产环境。

## 测量范围

每次请求都是新 requestId，实际执行：

```text
JWT 鉴权
  → Redis 滑动窗口限流
  → 单实例决策准入
  → MySQL 执行权/幂等检查
  → 已保存画像的 Redis Cache-Aside 查询
  → 定向与三家广告主一价竞价
  → 频控和预算预占
  → MySQL 决策结果提交
  → 返回响应
```

保留正常日志和审计，没有绕过后端业务逻辑，也没有重复 requestId 来命中已存结果。**不发曝光、点击、转化，不测 Kafka 或实际曝光结算**；这是决策接口吞吐，不是完整投放链路 QPS。

## 环境和数据

- API、k6、MySQL、Redis 共享本机 WSL2；CPU 为 Intel Core i7-8700、12 个逻辑 CPU。
- MySQL 8.0.46，buffer pool 128 MiB；Unix socket 连接，API 最大数据库连接数 30。
- k6 v2.2.0，固定到达率，预分配 256 VU、最多 512 VU，请求超时 2s。
- API 决策在途上限 256、排队超时 5ms、总决策期限 1s；Redis 全局准入 5000 请求/s。与应用配置一致，没有随压力修改。
- 1000 个已保存用户，均包含测试标签，画像提前预热；3 个广告主在同广告位出价 2/3/5 分，必须返回 5 分计划，响应中 advertiser count 必须为 3。
- 预算为 10,000,000 分，频控 100，保持开启。用户轮询，在本次负载下不会提前触顶。
- 每阶段仅清空独占 Redis 并重新预热；阶段内不清空。MySQL 保留前阶段决策，用不同前缀区分，记录随持续写入增长，并非每阶段还原相同数据库快照。
- 决策预占 TTL 仍为 30 秒。没有曝光确认，因此正常的过期预占由后续请求惰性清理；已确认支出应始终为 0。

## 业务结果与资源核验

客户端核验 requestId、获胜计划、素材、成交模式、5 分价格、3 个竞价广告主。响应不包含 userId，脚本从 MySQL 的持久化记录核对用户身份与请求序号映射。

450 QPS 三轮中：

- 持久化决策的用户、计划与价格均正确。
- 预占金额分别为 67,500 / 67,495 / 67,705 分，与 Redis 预占金额 Hash 合计一致，每条预占均为 5 分。
- 已确认支出均为 0，事件回执均为 0，符合“仅测决策、不发曝光”的范围。
- 用户频控快照最高为 14，低于上限 100；预算远未耗尽。
- 画像缓存命中增量分别为 27,001 / 27,001 / 26,999，无测量阶段画像回源。
- 每秒采样的在途决策最高分别为 98 / 103 / 110，goroutine 最高为 423 / 433 / 452。

800 QPS 失败阶段，在途决策采样达到 **256**，与配置门控上限一致，goroutine 采样达到 1000。256 约束的是执行中的决策，不是全进程 goroutine 总数。

CPU 数据以单核 100% 记录。MySQL、API、发压器和日志 I/O 共享资源，因此不能仅凭这些采样认定某一个模块就是根因。本次没有修改连接池、日志路径或进行阻塞剖析来抬高数字。

### 最后两次 HTTP 409

最后一轮服务器日志捕捉到两次 409，持续约 504ms 和 326ms，见 [错误样本](verification/decision-capacity/last-confirmation-errors.json)。它们已经计入错误率，没有重试后冒充成功。

当前服务代码对执行权获取设置 250ms 等待期限，某些获取超时会映射为 `ErrDecisionInProgress`，HTTP 层返回 409。因此 409 不一定说明客户端重复使用了 requestId；本次脚本没有主动重用 ID。此现象与执行权获取等待路径相符，但没有记录到足够的内部等待细节，尚不能精确归因为数据库连接池或某条 SQL 锁等待。

下一步可以对执行权获取耗时、数据库连接池等待和错误原因增加可观测性，再决定是否需要优化；本轮未混入修复，保持容量测量对象不变。

## 结果适用范围

> 使用 k6 对真实定向、竞价、预算频控预占及 MySQL 持久化的决策接口做阶梯压测，在本机环境以 450 QPS 完成三轮各 60 秒验收，P95 为 100～103ms，错误率低于预设 0.1%，无未派发请求；同时核对获胜计划、成交价、用户身份和预算预占，避免将未命中或幂等重放计入有效吞吐。

结果边界：三轮共两次 409，不是零错误；这是决策接口的当前环境验证档位，不包括曝光结算/Kafka，也不是生产绝对容量上限。
