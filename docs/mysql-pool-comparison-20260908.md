# MySQL 最大连接数对照实验与 pprof 修复

## 结论

2026-09-08 完成 **9 组交叉实验、27 个负载阶段**，全部通过既定保护与核账检查。当前默认保留 **最大连接 30、空闲连接 10、连接寿命 3m、空闲寿命 1m**。

在本次完整 Kafka 链路、当前过载保护与相同负载下，提高到 60/100 消除了连接等待，但没有观察到完成吞吐或端到端延迟的稳定改善。因此没有把“连接数 30→100”计为性能提升。

## 设计与环境

- 三轮顺序分别为 30→60→100、60→100→30、100→30→60，每个档位在三个顺序位置各出现一次。
- 每组新建 MySQL schema、Redis 进程、Kafka 三分区单副本 Topic/消费组以及真实 API；完成后清理。原业务数据库未用于压测数据写入。
- 每组 1000 个已保存用户；每阶段 3 个广告主、2/3/5 分出价，均满足定向且必须命中 5 分计划。每阶段额外 3 个完整流程用于预热，不计正式延迟，但计入金额核验。
- 每组依次执行 45 次/秒 ×20s 正常负载、100 次/秒 ×60s 过载、45 次/秒 ×30s 恢复。每轮最多执行决策和曝光/点击/转化，共 4 次 HTTP 请求、3 条事件；被拒绝的决策只有 1 次 HTTP 请求。
- 只改变 API 最大连接数；空闲连接数固定 10、最大寿命 3m、空闲寿命 1m。worker、relay、缓存、超时、频控和预算保持一致。
- 每个过载阶段都额外采集 20s CPU profile，开销对所有组一致；每约 1s 采样目标 API 的 DBStats，并保留开始/排空后的计数。后台工作也使用该连接池。
- i7-8700（6 核 12 线程）、主机约 32GB 内存；API、MySQL、Redis、Kafka 和 k6 共用 WSL。MySQL 8.0.46，max_connections=151，innodb_flush_log_at_trx_commit=1，sync_binlog=1。同机其他活动可能影响结果，详情见 environment.json。
- 九组使用同一 API 二进制，SHA256 在 design.json 和每组 proof 中交叉核对；源码快照、完整运行源码包和 CPU profile 已归档。

30 连接的等待分别为 170、62、0 次，累计 0.458、0.133、0 秒；60/100 各三轮均为 0。但等待次数统计的是连接获取，不是独立 HTTP 请求数，不能相除后宣称“请求等待率”。过载阶段各组采样到的在用连接峰值为 22–27，不能据此否认 30 档曾触顶；累计 WaitCount 记录了采样间隔内的等待。

## 分析线索

1. **空闲连接反复关闭值得独立验证。** 过载阶段 MaxIdleClosed 增量分别约为每组千次；三档中位数为 1117、1348、1300。这是空闲数量上限触发的关闭，不是连接寿命到期。下一步可固定最大连接数，再单独比较空闲上限 10/20，不能把这次结果当成那个实验已完成。
2. **CPU profile 不等于 SQL 等待分析。** 第一组 30 连接的 20s 采样中，flat CPU 较多落在系统调用和 runtime.futex；这不能直接证明某把业务锁或数据库提交就是唯一瓶颈。同步审计、事务提交的进一步优化仍需结合 SQL 耗时和阻塞观测。
3. **对象池仍未接入。** 本次没有用未接入的 sync.Pool 宣称减少分配或 GC；若要做内存优化，需要另外采集分配证据。

## 工具修复

- pprof 默认关闭，显式配置 loopback 地址，每个 API 可用不同端口；跟随 Context 关闭。
- `/debug/instance` 返回 API 地址、PID、启动时间及池统计，不返回 DSN、环境变量或 token。
- 分析脚本不再自动启动 API；采样前核对实例，拒绝端口不匹配，采集后检查进程未更换。
- 保存 `.pprof`、文本 top 和实例 JSON 后正常退出。交互式 `-http` 单独启动，不再伪装为 HTML 文件导出。
- CPU、heap 采集已实际验证；未启用 block 采样会明确拒绝。Duration 只控制 CPU 采集时长，其余类型是采样快照。
- Go 全量测试及 vet 通过；保留修复前失败测试记录与修复后验证。

工具使用见 [pprof 指南](profiling.md)。
