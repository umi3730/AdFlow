# Kafka 完整链路容量复测（死锁恢复修复后）

## 最终结论

2026-09-08：当前本机配置下，**45 轮业务/秒（约 180 HTTP QPS、135 事件/秒）**通过三组各 120 秒的完整链路 SLO、核账和队列趋势检查。这是本次按 5 轮/秒分辨率找到的最高全部通过档位，不是绝对系统最大值或生产容量保证。

50 轮/秒三组各 120 秒通过有限窗口 SLO，但第三组队列显著增长；55 轮/秒长测延迟超标；60/65 轮长测进一步出现结算超时待核对。因此不把更高档位包装为持续平稳吞吐。

本次保留全部失败记录，只修改了报告核验工具及文档，未调整业务实现、超时、连接池、worker 或 relay 参数。五次隔离实验的数据库、Topic、消费组和临时进程均已清理；本机原 API/前端保持可访问。

## 口径与环境

- 真实 k6 v2.2.0 固定到达率。每轮一次决策、曝光/点击/转化各一次回传，即约 4 次 HTTP 请求、3 条 Kafka 事件。
- 1000 个保存且预热的用户；每阶段 3 个广告主出价 2/3/5 分，必须命中 5 分计划。每阶段额外 3 次完整预热不计入正式测量，但计入金额核验。
- API、MySQL 8.0.46、独立 Redis、Kafka 三分区单副本和 k6 共用本机 WSL。i7-8700，6 核 12 线程，主机约 32GB 内存，WSL 可用总内存约 15.5GiB。压测包含观察器查询和请求日志开销。
- MySQL `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`；默认隔离级别 RR，修复涉及的事务显式使用 RC。未调大连接池或 worker，未修改 Outbox 每批 100 条、500ms 轮询策略。
- 每次独立实验新建数据库、Redis 进程、Kafka Topic/消费组；保留同一实验前序阶段的数据。过载实验中止后，下一档另开环境，不继承未处理积压。
- 门槛沿用旧版：决策 P95 <300ms，四次 HTTP 受理 P95 <1s，统计提交可见 P95 <5s，业务错误率 <0.1%，无未派发/No-Ad，停发后 10 秒内排空，事件/金额/幂等核验全部通过。
- 统计完成由每 250ms 的查询首次观察到三类事件均已提交来计时，包含观察误差。不能用 HTTP 202 或 Kafka lag=0 替代整条链路完成。
- 队列辅助检查排除前 5 秒，对比派发期间前/后 5 次采样的平均待处理事件；增长超过一批 100 条提示不可宣称队列平稳。

65 轮长测的 HTTP 流程 7801 轮全部受理，但核验快照只有 5125 轮完成统计，另有 232 条结算处于 RECONCILE，其余任务仍可能继续变化。已完成子集的 P95 为 29.117s，**不能当成全量 P95**。此阶段 `drainAfterLoadSeconds=0.158` 是检测到 RECONCILE 后提前返回的耗时，不是排空用时。后续 60 轮阶段预热未排空即中止，没有正式测量；因此另外启动了独立 60 轮实验。

独立 60 轮实验共受理 7200 个完整流程、21600 条事件；核验快照只观察到 4512 轮统计完成、268 条 RECONCILE。决策 P95 356ms、HTTP 受理 P95 1.057s，均超门槛。1 次 409 的根因未独立定位，不据此推断一定是重复请求。

55 轮实验没有 HTTP 错误或 RECONCILE，账目全部对齐，但待统计事件前段均值 200.2 → 末段 1147，增长约 947 条；停发后 6.31s 排空不能消除持续积压的事实。

| 2 | 6001 / 6001 | 1.429s | 1.03s | 107 → 117 |
| 3 | 6001 / 6000 | 4.445s | 3.81s | 96.2 → 597.2 |

三组共 18002 次正式派发，18001 个完整流程、54003 条正式事件处理完成。第三组有 1 次决策 HTTP 409，错误率仍低于预设 0.1%；无 dropped iterations、No-Ad 或 RECONCILE，账目/幂等/最终 Kafka lag 检查通过。

但第三组队列均值增长约 501 条，超过一批 100 条的辅助警示门槛，因此**不能把 50 轮/秒写成持续不积压的容量**。脚本 `confirmedBusinessRoundsPerSecond=50` 仅表示三组有限窗口 SLO 通过；还要一起阅读 queue-trend.json。

## 瓶颈判断与后续

采样显示高负载时未结算曝光数量持续增长，大量事件尚未发布；已经发布的事件通常很快完成消费。由此可以把排查重点放在**结算与入箱/发布的数据库路径**，不能把问题称为 Kafka broker 吞吐不足。

45 轮测试期间的 Performance Schema 累计抽样中，COMMIT 21319 次、平均 11.221ms，审计 INSERT 13942 次、平均 11.113ms，累计耗时排名靠前。审计中间件在请求处理后同步调用单条 INSERT，额外增加数据库写入负担。这是包含预热和此前请求的阶段中抽样，不是完整测试的精确请求计数，也不能把并发语句累计耗时相加当作墙钟耗时；只用于定位候选热点。原始抽样随 45 轮实验归档。

当前结算 worker 每次领取 4 条，串行执行 Redis 确认和 SQL 完成；有工作会立即继续，不存在“每 200ms 只处理 4 条”的固定上限。Outbox 自身每批 100 条、500ms 轮询，名义调度预算约 200 事件/秒（约 66.7 完整轮/秒），还未扣除数据库、发布等开销；这个算式不是实测服务容量。

长测发现的是另一类边界：即使瞬时死锁可重试，持续过载也会让结算等待超过 Redis 预占 30 秒期限，进入待核对。此前的死锁恢复修复不等于过载保护。下一步优先为异步积压增加观测与准入背压，再分别测结算 SQL 耗时及安全的有界并行；不能简单延长预占或无限增加 goroutine。
