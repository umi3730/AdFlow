# 当前并发设计

依据 2026-09-10 代码核对；本地运行配置示例来自既有启动记录。下面的上限是配置和实现约束，不是已测得的服务器容量。

## 浏览器：固定在途轮次

`web/lib/user-pool-simulator.ts` 用 `inFlight` 计数。设置并发 100 后启动最多 100 轮，每轮完成后补发一轮，直到达到总轮数或派发时长。每轮按顺序执行决策及启用的曝光、点击、转化，共用一个 AbortController 和整轮超时。

这里的 100 是逻辑在途轮次，包含浏览器排队、网络和事件回传，不代表 100 个后端连接或线程。浏览器连接限制会影响真正到达后端的并行请求数量。

## API：限流、并发许可和处理超时

`internal/decision/application/admission.go` 在核心决策之前执行：

1. Redis 模式使用共享滑动窗口，默认每秒最多 5000 次准入，超限返回 429；多个 API 使用相同限流键时共享此速率限制。默认内存模式使用进程内令牌桶，实际模式以启动配置为准。
2. 每个 API 实例有容量为 256 的 buffered channel。请求进入核心决策前占一个位置，完成、失败或取消时通过 defer 归还。它限制同时执行的决策，而不是预先启动一个固定大小的 goroutine 池。
3. 位置满时最多等待 5ms，仍取不到返回 503，避免长期堆积。
4. 取得许可后的核心决策超时由配置决定，代码默认 100ms，既有本地运行配置使用 1s。它不是所有 HTTP 接口的统一超时，也不包含整个浏览器业务轮次。

数据库连接池每个 API 默认最多 30 条打开连接、10 条空闲连接，决策、事件、后台任务等共享这个池。因此 256 个决策许可不等于同时执行 256 条 SQL。后台其他接口也没有自动继承决策准入限制。

Kafka 模式还会对新决策检查异步积压：后台每 200ms 尝试采样结算与 Outbox 队列，达到任一高水位就阻断，两个队列都回到各自低水位才恢复。快照不可用或至少 1s 未更新时停止新决策准入。已保存决策的合法重试在业务层复用原结果，但仍经过前门限流与并发许可。该机制是采样反馈，不是严格的跨实例在途数量限制。

## 并发下的业务正确性

- 请求参数绑定和 MySQL 执行租约协调重复 requestId，只有有效 owner 可以提交；每次执行的预留 token 分离，避免失败执行释放其他执行的资源。
- Redis Lua 原子执行预算和频控各自的预占判断；曝光结算时把两者确认和幂等凭证写入放进一次 Lua 操作。
- 短事务、所有权检查、幂等事件 ID 和成交快照共同保护结果；仅有进程内 mutex 不足以保证多个 API 之间的正确性。

## 异步事件：多 worker 领取、按分区消费

- 每个 API 启动一个结算 worker 和一个 Outbox relay。MySQL 使用 `FOR UPDATE SKIP LOCKED`、租约和所有权校验分配任务，其他 worker 跳过已经锁定的行。
- 结算 worker 每批最多领取 4 条，租约为 15s，在该 worker 内顺序结算。领取最多使用 2s，每条任务的 Redis 确认与数据库完成共用 2s 期限；这个 4 是批大小，不是 4 个并发 worker。
- 提前退出时，使用脱离原取消信号且限时 1s 的清理上下文归还未完成任务，并校验 owner。进程直接中断时依靠租约接管；若预留已失效且没有结算凭证，仍进入待核对，不能盲目补扣。
- Relay 每批最多领取 100 条，批量发布到 Kafka。结算完成前不发布，点击和转化还要等待曝光的发布凭证。
- Kafka 用 requestId 作为 key；同一个请求的事件进入同一分区。消费者在每批拉取中并行处理不同分区，同一分区内按顺序/批次处理，成功后提交 offset。
- Kafka 重投或进程重启仍可能导致重复处理尝试，消费端按 eventId 幂等计量，不依赖“只投递一次”的假设。

实际扩容应结合请求耗时、数据库连接等待、锁等待、结算积压、Kafka 分区和 CPU 判断，不能只把 channel 容量调大。
