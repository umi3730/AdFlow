## 缓存协议

此前写入把本次输入直接写到 Redis，同时只使用进程内 keyLocks 保护回填。已复现两个实例交错时，源数据为 score=99 而缓存退回 score=10；旧写操作晚完成也可能覆盖新缓存。

本轮采用带代次校验的 Cache-Aside：

1. 热缓存命中仍直接读取；未命中时，在查数据源之前取得 Redis 中的随机代次。
2. 读取结果只能由 Lua 在代次仍相同时回填，正缓存和负缓存都使用这一条件。
3. 保存或删除数据后，Lua 原子切换随机代次并删除缓存。写入不再直接把自己的输入放入缓存，因此两个写入完成顺序颠倒时不会缓存旧输入。
4. 本实例正在合并的读取也按代次区分；失效后的新查询不会加入旧代次的读取任务。
5. 代次丢失或到期后，旧回填失败，不能把“没有代次”当成允许写入。新代次为随机 token，避免清理后从零计数带来的重复代次。
6. 在等待本地锁后再次检查缓存，保留并发未命中的合并效果。代次键具有有界 TTL，使用 g2 命名空间隔离旧协议的缓存，未执行全库缓存清空。

## 明确边界

- 与写操作重叠的读取可以返回自己先前读到的快照；保证的是已完成失效之后，旧查询不能污染后续缓存。
- 数据库更新和 Redis 失效仍不是同一个事务。失效失败会向调用方返回错误；读取遇到 Redis 故障时回源且不盲目回填。
- 进程在数据库提交后、失效前崩溃，仍可能依赖 TTL 或重试恢复。本轮不宣称跨存储强一致，持久化失效任务可以作为后续增强。
- 数据源写入即使返回不确定错误，也尝试失效，避免遗漏可能已经提交的修改。
- 需要所有 API 实例一起升级；旧版本写入不会遵守新代次协议。本机 18080 和 18081 已完成替换，不需要新数据库迁移。
