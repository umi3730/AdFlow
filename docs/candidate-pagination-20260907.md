# 候选读取完整性修复（2026-09-07）

## 问题与修复

候选 Provider 原先只读取一页 100 条 ACTIVE 计划，同一广告位的后续计划完全不会参与决策。这是正确性缺陷，不是并发或吞吐上限。

当前每页读取 100 条，用上一页最后一条计划 ID 作为游标（AfterID），按 ID 升序继续读取。普通管理列表没有传游标时保留原有排序和分页行为。每页只发一次批量素材查询，最多包含 100 个计划 ID，不退回逐计划查询。

- 终止依据是原始页大小，与有效候选数量无关；整页都过期或尚未开始，仍继续读取后面的计划。
- 游标避免前面记录插入、暂停或删除造成 OFFSET 位移而跳过后续记录。
- 请求取消、后续计划页失败、后续素材批次失败均返回错误，不返回或缓存半份候选。
- 对重复 ID 去重；仓储未推进游标时终止报错，避免循环读取。
- 保留开始时间包含、结束时间不包含、活动版本和素材状态等既有规则。

## 前后证据

同一回归构造 201 个计划，每个计划只匹配自己的标签，用户只满足第 201 个计划：

- 旧实现：返回未命中 targeting_miss，回归失败。
- 新实现：命中 campaign-0200 及其素材，回归通过。

旧代码通过 Go source overlay 从记录的 baseline commit 加载，没有临时覆盖工作区源文件。完整日志在 [before.jsonl](verification/candidate-pagination/before.jsonl) 与 [after.jsonl](verification/candidate-pagination/after.jsonl)，版本与文件摘要在 [metadata.json](verification/candidate-pagination/metadata.json)。这些文件进入文档目录，未放在被忽略的 work 中。

新增回归覆盖：0/99/100/101/200/201 个计划、真实决策引擎命中尾页、首批全为无效时间段、页失败后缓存重试、取消、MySQL 查询与参数、插入前排记录、删除/暂停前排记录、游标不推进。MySQL 使用 sqlmock 验证查询契约，不等同于真实数据库压测。

## 成本与边界

全部计划有效时，101 条计划对应 2 次计划页查询和 2 次素材查询；201 条对应各 3 次。恰为整页时额外读取一张空页确认结束。原来的 2 次查询只覆盖最多 100 条，不能把它与完整读取直接比较为延迟优化。

这是多次查询组成的配置读取，不是数据库一致性快照。读取期间修改规则或新增游标之前的计划，仍可能到下一次候选缓存刷新才可见；本轮不改变已有五秒 TTL 和一致性约定。没有增加新限额来掩盖尾部遗漏。

本轮执行 Go 候选及仓储回归、Go 全包测试、vet 和 API 编译。没有重跑容量基准；本机无 CGO/C 编译器，race 由已有 Linux CI 执行。没有重启当前本地服务，避免清空现有内存演示数据；运行中的服务仍需后续重启加载新二进制。
