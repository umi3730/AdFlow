# 用户池模拟超时修复与实测（2026-09-07）

## 问题与修改

用户在切换持久化异步模式后，以 100 个在途轮次、30 秒派发、单轮超时 5000ms 运行。原截图显示派发 662 轮，421 轮超时，P50 达到 5001.4ms。对应后端日志中，成功决策平均耗时约 484ms；浏览器整轮还包含连接等待及事件回传，因此前端会更早耗尽整轮超时预算。

定位到两处可重复的问题：

1. 一次性参数 SQL 每次都走 prepare / execute / close。当前 Windows → WSL MySQL 链路中，30 次 `SELECT ?` 的中位耗时为 45.657ms；相同参数查询启用驱动插值后为 0.505ms。一次决策执行多条 SQL，额外网络往返被放大。这是该本机连接路径的观测，并非 MySQL 普遍具有 45ms 固定延迟。
2. 原队列通过范围 UPDATE 领取任务，持锁期间还查询其他表；结算完成按 requestId 更新 Outbox 又缺少对应索引。真实并发测试捕捉到 MySQL 1213 死锁，部分事件写入也被阻塞。

最终修改：

- 在统一 MySQL 连接入口启用驱动 `InterpolateParams`，继续使用参数化调用及驱动自身的转义规则。
- JSON 参数统一使用 `json.RawMessage`，避免普通 `[]byte` 被插值为 binary 字符串后导致 MySQL JSON 写入失败。涵盖竞价、决策、画像、结算、Outbox、审计及内置样例。
- 两类队列在 READ COMMITTED 事务中用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取，再按本批主键更新。其他 worker 跳过已锁定任务，不等待同一范围。
- 新迁移 `000011_outbox_request_index` 增加 `(aggregate_key, status)` 索引，把结算完成/失败的 Outbox 更新限制在对应请求范围。

没有增加模拟器超时、降低并发、删除幂等检查或关闭预算/频控。两个正式本地 API（18080、18081）均已部署修复，数据库迁移已执行到 000011。

这是浏览器连接受限场景的传输模型对比，不是真实浏览器的网络时序记录，也不是 k6 服务端容量测试。原版的取消回调可能晚于计时器触发，因此该模型部分超时样本记录的最终耗时超过 5 秒。

仅开启插值的中间版本还出现 4 次失败，随后补齐队列领取和索引修复；该中间记录保留为 `after.json`，最终结果为 `after-final.json`。
