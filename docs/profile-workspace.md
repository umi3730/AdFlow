# 用户画像与定向诊断

## 操作流程

用户选择项只显示用户 ID，标签和字段在详情区查看。新建画像默认填入 user-0001 一类的编号；成功创建后推进本机编号，编辑已有画像不消耗新编号，手动输入优先。编号避开已加载页面中的用户并保留原有保存前存在性检查，但不是跨浏览器的全局唯一 ID 分配器。

保存成功后自动回到新建表单，而不是停留在只读 ID 的编辑状态；失败则保留输入。已有画像的 ID 可编辑，但改为不同 ID 时属于「另存为新用户」，提交前核对目标 ID 是否已存在，原用户和历史关联不改动。成功另存后才推进编号，不把复制操作描述成主键重命名。

1. 打开「用户画像」，创建用户并保存标签、设备、分数和额外字符串属性。
2. 左侧表格读取真实后端数据，支持用户 ID 模糊搜索、标签/设备精确筛选和每页 20 条分页。
3. 点击「查看 / 编辑」回填完整画像；额外字段不会因只编辑设备或分数而被静默丢弃。
4. 点击「发起决策」进入调试页并带入用户 ID；也可以在调试页快捷选择前 100 个已保存用户，或手动输入 ID。
5. 决策后查看中文 No-Ad 原因及当前定向检查：缺标签、缺字段、值不匹配、命中排除条件。`device` 和 `platform` 是不同字段，不自动互换。

## 边界

- 画像列表由独立 `ProfileCatalog` 端口提供；内存与 MySQL 实现，缓存适配器将列表读取转发到源存储，不扫描 Redis。
- MySQL 列表使用参数化筛选。包含查询和 JSON 属性筛选暂未针对大用户池建立专用索引；不能据此宣称百万用户检索能力。
- 编辑使用已有 PUT 全量替换语义，当前没有版本号并发编辑保护。
- 诊断复用领域 Evaluator，但读取的是检查时的候选快照，不是原决策的历史快照。候选缓存刷新延迟仍适用。
- 诊断不注入预算、频控和决策存储端口，不产生预占；预算、频控等 No-Ad 原因以真实决策结果为准。
- 内存模式重启会清空临时计划和画像；需要持久化时使用已有 MySQL 适配器。
- 固定并发用户池模拟已实现，并提供内置演示用例入口，见 `user-pool-simulation.md` 和 `demo-data.md`；本页单次调试仍不是容量压测。

## 回归覆盖

- 领域层：ALL / ANY / NONE 解释与 Match 一致。
- 应用层：多次定向检查不消耗一次性预算与频控额度。
- 适配器：内存筛选、分页、数据克隆隔离；MySQL 参数化查询的 mock 测试。
- HTTP：列表、详情、缺失画像、无效分页、定向检查响应。
- 前端：类型检查、lint、显式表单提交检查和已有规则转换测试。

本轮不等同于真实 MySQL/Redis/Kafka 环境全量验收。
