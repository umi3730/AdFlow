# MySQL 空闲连接上限 10 / 20 对照记录

## 当前结论

2026-09-09 固定最大连接数 30，按 **10→20、20→10、10→20** 完成六组空闲连接上限对照。暂时保留默认 **30/10**。

本次观察到：每个 60 秒过载阶段，`MaxIdleClosed` 增量中位数从 **1257 降至 140，减少约 88.9%**。这表示因空闲数量超限而关闭的连接减少，不能解释成数据库请求减少、连接创建次数精确减少或 QPS 提升。

这批数据有两项限制：10 连接第三轮出现业务错误和未派发；测试期间工作区源码发生变化，原脚本逐轮读取的是实时源码，而 API 二进制在整组开始前构建。因此**保留全部测量结果作为调参线索，不据此发布新的容量结论，也暂不把 88.9% 写成已上线的简历优化成果**。源码版本固定后的重复验证仍待执行。

## 负载与环境

- 六组都记录了同一 API 二进制 SHA256：`064f7038c887d1ce80e43a16eb8533af139297d1edef27d1f59ed7ca33f1dec1`。
- API 最大连接 30；只改变空闲数量上限 10/20；连接寿命 3 分钟、空闲寿命 1 分钟。
- 每组使用独立 MySQL schema、Redis 进程和 Kafka topic/消费组，1000 个已保存且预热的用户。正常业务数据库不参与写入。
- 正常阶段：45 次决策尝试/秒 ×20 秒；过载阶段：100 次/秒 ×60 秒；恢复阶段：45 次/秒 ×30 秒。过载不通过时按原有规则结束该组，不补测或删除失败数据。
- 完整业务包括决策、曝光、点击、转化，最多 4 次 HTTP 调用和 3 条 Kafka 事件。明确的过载拒绝单独计数，不作为完整业务吞吐。
- 每个过载阶段采集 20 秒 CPU profile；采样目标 API 的 DBStats，使用阶段前后累计计数的差值。
- i7-8700，6 核 12 线程，约 32GB 内存；Go 1.27，MySQL 8.0.46。API、负载工具和依赖共用 WSL/本机资源；不是独占机器实验。测试期间有其他开发活动，未量化其 CPU/IO 干扰，不能将波动单独归因于空闲上限。

第 5 组正式发出 5993 次尝试，其中 2345 个完整流程、3637 次预期拒绝、11 次非预期业务错误；另有 8 次计划迭代未派发。命中决策 P95 为 469.31ms、受理 P95 为 1.278s，统计可见 P95 为 5.437s，均未通过相应门槛。API 日志可见一次 HTTP 409，其余错误原因未从现有记录中完整确定，不宣称已定位或修复业务根因。

六组共执行 17 个正式阶段：**48155 次尝试、30611 个完整流程、17533 次预期拒绝、11 次非预期错误、91833 条事件、139988 次业务 HTTP 调用**。所有阶段已经受理的事件、预算和统计最终核账一致，预占归零、重复事件幂等和 Kafka 最终 lag 检查通过；这不等于所有阶段性能通过。每阶段额外 3 次预热流程不计入以上正式计数。所有组的临时资源清理记录均成功。

## 先前失败系列与时钟处理

第一次系列保存在 `verification/idle-comparison-clock-failure`，六组均失败。WSL 日志出现墙钟后退，API 日志中可见约 0.718 秒倒退，随后出现事件 HTTP 422。此前 NTP 状态记录偏差约 -0.783 秒、轮询间隔 32 秒。墙钟回退会让后续点击/转化的服务端时间早于此前事件，从而触发顺序校验。

这是实际观察到的环境问题，不把其精确机制全部归因于 NTP，也没有关闭业务事件顺序校验来掩盖错误。

经用户明确同意，09:49:45 临时暂停 WSL `systemd-timesyncd`；先检查 60 秒时钟稳定，再执行第二次系列。每组比较墙钟和单调时钟，偏移超过 50ms 会将实验标记失败；六组最大观测偏移均未超过 0.0155ms。10:06:30 已在 `finally` 中恢复自动校时，并实际核验服务为 `active`，没有更改 Windows 时间。

第一系列保留为环境失败证据，不参与 10/20 参数汇总；两系列二进制摘要不同，不能称为同一个二进制。以上表格全部来自第二系列。

## 源码留档问题与工具修复

第二系列六次 API 二进制摘要一致，但运行器每轮读取工作区源码来记录 SHA256。`cmd/api/main.go` 在执行期间发生变化，使部分记录指向编译后的工作区版本。已从旧归档和当前文件恢复能匹配指纹的快照；第 3 组的中间版本无法恢复。原始 proof 未改写，不能将恢复的文件说成完整可复现的二进制源码。

- 独立审计默认仍拒绝找不到源码指纹的记录。显式 `--measurements-only` 才允许继续核对原始 k6 数量、分位数、DBStats 差值、核账和失败门槛；输出保留 `verified: false` 与缺失的源码项，`measurementsVerified: true` 只表示测量核对通过。
- 修复后的对照脚本先复制独立源码目录，从该目录构建 API 和运行器，并从该目录加载迁移、负载脚本和源码指纹。构建后及每轮前后核对快照；不再使用共用二进制输出路径。
- 新增 `-PrepareOnly`，仅验证快照和 Linux 交叉编译，不执行数据库压测。该路径已实际构建通过；修复后的脚本尚未再次完成六组负载实验。
- 增加空闲参数校验、墙钟偏移检测及审计回归测试。后处理工具快照单独放在 `post-run-tools`，不冒充压测时版本。

收尾验证：当前工作区 `go test ./...`、`go vet ./...` 均通过，3 个审计回归用例通过；283 个文件的独立快照及 Linux API/运行器编译通过。这些属于工具修改后的检查，不替代新一轮性能实验。详见 [验证记录](verification/idle-comparison/post-run-validation.json)。
