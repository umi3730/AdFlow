# 上手体验与校招面试审阅（2026-09-07）

后续更新：上手引导、功能分组和双实例画像缓存修复已落地，见 [第一阶段交付](onboarding-cache-improvements-20260907.md)。下文保留原审阅发现及当时的失败证据。

目标岗位为校招/实习 Go 后端。本轮审阅当前代码与近期验证记录，补充上手文档及一个隔离复现；没有修改运行中的界面、业务配置或缓存数据。

## 判断

当前项目已有足够支撑校招深入讲解的主线：不可变计划版本、内部一价竞价、Redis 预算与频控、请求执行权、Outbox 主动结算、Kafka 幂等消费，以及带失败记录的真实优化。

优先工作是让这条主线容易使用和讲解，并补足当前实现的边界。技术模块都放在导航里，但第一次打开的人缺少“我该先做什么”的指引。

## 上手体验的具体缺口

| 发现 | 当前依据 | 建议 |

| 首页从指标和新建计划开始，没有入门路线 | AdFlowConsole 默认 dashboard；Dashboard 直接展示统计和计划表 | 增加可收起的「三分钟体验一次投放」，完成后仍可从帮助入口重开。 |

建议首版引导保留现有配色与模块结构，不新增强制弹窗或整屏术语说明。用少量可点击步骤说明“当前要做什么、完成后去哪里、预计看到什么”，进阶参数折叠，帮助入口随时可重开。

## 后端优先级

### P1：多实例画像缓存可能被旧值回填

`internal/decision/adapter/profilecache/store.go` 的 keyLocks、inFlight 都属于单个 Store。写入和回填受本实例锁保护，但两个 API 实例之间没有版本约束。

本轮隔离复现的交错：

1. 实例 A 未命中缓存，从数据源取得 score=10，暂缓回填。
2. 实例 B 将数据源和缓存都更新为 score=99。
3. 实例 A 恢复，把 score=10 回填到共享缓存。
4. 数据源仍为 99，而实例 B 下一次缓存命中返回 10。

这会表现为“用户明明保存了新画像，决策却仍使用旧属性”，也可能发生在删除之后。建议先固定双实例回填/更新/删除交错测试，再选择带版本的缓存写入和失效方案；简单再加一个进程内锁无法解决。

复现通过 Go overlay 临时加入测试，断言“不返回旧值”失败，结果为 `persisted score=99, cached score=10`。这是明确的缺陷证据，不是通过报告。本次使用内存数据源、两份真实缓存适配器和 miniredis，不是线上故障统计，也没有改动当前业务缓存。源码与原始记录在 [verification/onboarding-review](verification/onboarding-review)。

### P1：把真实依赖测试变成可复现入口和自动门禁

近期已有真实 MySQL/Redis/Kafka 通过记录，但 `.github/workflows/ci.yml` 仍只运行普通 `go test -race`，未运行 integration build tag。应让关键集成测试在独立依赖和测试库中自动执行，保存配置、代码版本与结果。旧版、新版差异要能在另一台机器上复现。

### P2：按一个请求解释完整处理过程

将保存的决策、成交价、结算任务、Outbox 状态和已处理事件按 requestId 联查，做只读详情页。它能直接回答“为什么选这个广告、有没有扣费、统计为什么还没增加”，也便于面试现场演示故障恢复。不要把当前配置的重新解释冒充原请求的历史轨迹。

### P2：补齐对账、留存与业务边界

RECONCILE 目前有隔离和可见性，但没有受控人工核对闭环；decisions、receipts、settlements 等历史表缺少完整清理/归档策略；审计仍为业务操作后的尽力写入。先定义这些保证与边界，再按实际需要补实现，不必在校招前把全部生产能力堆齐。

## 推荐推进顺序

1. 先做新手入口和清晰的单次演示路径，让使用者能完成一次投放并解释各阶段。
2. 修复已复现的双实例缓存回填问题，补正反例和更新/删除交错测试。
3. 把现有真实依赖测试和启动步骤变成稳定的一键验收入口，并接入自动执行。
4. 增加单请求处理详情，用已有数据讲清楚决策和结算，不急于扩展新的业务模块。

校招介绍可以定位为“基于 Go 的广告决策与异步计量系统”。重点讲业务约束、选型取舍、故障复现和验证证据；内部竞价不是外部 OpenRTB 平台，现有管理员权限不是广告主多租户隔离，浏览器 100 并发也不是生产峰值承诺。
