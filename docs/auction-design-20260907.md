# 竞价方案与实现（2026-09-07）

后续已补请求参数绑定、执行租约和预占所有权隔离，见 [请求执行修复](decision-execution-fix-20260907.md)。内存结果保留调整为 5 分钟，预占仍为 30 秒。

## 实施前的问题

- 决策服务按 CampaignID 升序尝试候选，没有按出价比较。
- ImpressionCostFen 用于预算预占和曝光确认，不是独立出价配置。
- 计划版本与决策结果都没有保存竞价策略、出价和成交价。
- 定向、素材、频控、预算、请求幂等和事件链路已具备，可以复用。

以下旧行为已由本轮一价竞价补齐。原固定成本计划仍作为兜底，不会被静默当成出价。

## 本轮实现

采用内部单广告位的一价竞价：合格计划中最高出价者优先，实际成交价为中标者自己的出价。它不是外部 DSP 实时询价或完整 OpenRTB 对接。

1. 先排除无有效素材、不满足定向和不在投放期内的候选。
2. 独立出价参与降序排序，同价基于 requestId 与 campaignId 的稳定哈希打散；同一请求结果可复现，不永久偏向较小计划 ID。
3. 依次尝试真实频控和预算预占。最高价无法预占时释放已经取得的资源并尝试下一名；不能只读取一个非原子的预算余额就认定可投放。
4. 中标按成交金额预占预算，曝光确认该预占；未曝光超时释放。重复请求不得重拍或重复扣款。
5. 决策持久化获胜计划版本、竞价策略、出价与成交价。历史结果不能从当前已修改的计划规则重新推算。
6. 保留明确的旧计划兼容策略：不得在无说明的情况下把所有历史曝光成本直接变成出价，历史版本也不改写。

## 计价单位取舍

| 选择 | 收益 | 需要处理的边界 |
| --- | --- | --- |
| 每次曝光出价，金额为整数分 | 复用现有预算和预占金额精度，容易先做完整 | 明确这是内部简化竞价，不称为 CPM/OpenRTB 实现 |
| CPM，按千次曝光出价 | 更接近 OpenRTB 的报价口径 | 单次金额可能小于一分钱，需要定点金额精度与累计结算设计，不能把每次费用四舍五入到分 |

[IAB OpenRTB 2.6](https://github.com/InteractiveAdvertisingBureau/openrtb2.x/blob/main/2.6.md)定义了一价、二价等 auction type；[OpenRTB 3.0](https://github.com/InteractiveAdvertisingBureau/openrtb/blob/main/OpenRTB%20v3.0%20FINAL.md)明确 bid price 的 CPM 口径。本方案参考概念，尚未实现这些协议。

## 要体现到产品中的内容

- 计划规则新增明确的竞价配置与出价单位。
- 决策页展示本次获胜出价、成交价和策略；当前定向诊断与历史竞价结果分开。
- 模拟结果按计划统计命中和成交金额，以实际后端响应为准。
- 提供三个同人群、不同出价的独立演示计划，验证价格竞争；修改价格需发布新版本。

## 核心回归

- 高价获胜；最高价不匹配/频控已满/预算不足时正确选择下一名。
- 同价可复现且不依赖计划 ID 固定顺序；统计验证跨请求分布，而非承诺严格轮询。
- 开始/结束边界再次验证，过期的缓存候选不得中标。
- 排序不占用预算；失败候选不留下预算或频控预占。
- 同 requestId 重试保持中标结果和价格，重复曝光只结算一次。
- 规则重新发布后，历史决策仍保留原成交信息。
- 多并发竞争不能超预算、超频控；金额精度与取整按选择的计价模型测试。

## 当前交付与边界

已选择每次曝光出价，整数分计价。第一版不实现 CPM、外部 DSP 询价、OpenRTB、二价或预算 pacing。

广告主标识和显示名称记录在不可变计划版本内，由平台管理员配置；不是广告主登录账号或多租户隔离。标识统一为小写 ASCII；相同标识作为同一广告主，不按显示名称分组。

同一广告主先从满足定向/时间/素材条件的计划里选最高价代表；代表随后因预算或频控失败时，该广告主本轮退出，不再尝试其低价备用计划。竞价均未成交时才尝试旧固定成本计划。相同请求的同价打散可复现，但不提供对恶意构造 requestId 的抗作弊保证。

新增 campaign_versions.auction_terms 和 decisions.pricing，由迁移 000008_first_price_auction 提供。旧版本没有 auction_terms 时沿用固定成本。新匹配决策保存策略、广告主、出价、成交价、版本、参与广告主数量、顺位及预算/频控拒绝计数；无竞价信息的历史决策不补造价格。内存历史仍受原有 TTL 约束，持久留档需使用 MySQL。

前端按 campaign.auctionSupported 判断后端支持能力；旧后端不会开放竞价配置。Agent 继续只生成定向和固定成本草稿，竞价及广告主必须由管理员显式配置。

### 演示与验证

默认初始化额外提供三个竞价计划：星河游戏 2 分、风铃互动 5 分、北辰科技 3 分，共用 auction_demo 人群。demo-auction-user 是独立的演示画像。各持久化种子分组仅安装一次，删除后不会在重新部署时复活；内存新进程会重新创建。

独立本地 API 18081 与前端 3001 提供竞价预览。现有 18080/3000 服务及其内存数据未重启或迁移。正式切换时先备份持久数据、应用迁移，再更新后端；内存服务重启会丢失当前内存状态。

真实 HTTP 验证见 [http-smoke.json](verification/auction/http-smoke.json)：5 分胜出，暂停最高价后 3 分胜出；同 requestId 不重拍；同 eventId 重复曝光只累计一次。脚本为 tests/auction-smoke.mjs，只用于独立本地测试实例。

并发回归中 100 个请求竞争 50 分预算、单次 5 分，恰好 10 次中标，总预占 50 分。另覆盖最高价胜出、预算/频控降级、败选释放频控、同广告主去重、同价稳定分布、过期缓存候选排除、固定成本兜底和版本隔离。

MySQL 字段往返和事务 SQL 通过 sqlmock 检查；本轮未运行真实 MySQL 竞价持久化测试，也没有容量压测。不得把本轮功能回归的请求数量当作 QPS。


前端模拟最近记录同时保留获胜计划、广告主和本次单价，直接取决策响应而非当前计划配置。浏览器竞价用例完成 3 轮完整事件链、12 次 HTTP 调用，失败为 0；决策页显示风铃互动以 5 分胜出。

最终验证：Go 全包测试与 vet、98 项前端回归、TypeScript、lint、前端构建通过。竞价 Go 回归原始记录见 [go-auction.jsonl](verification/auction/go-auction.jsonl)。本机未运行 race 检测（无 CGO/C 编译器），真实 MySQL 迁移和跨实例同 requestId 并发提交仍需专门验收；本轮幂等 HTTP 验证是串行重试，100 并发预算回归使用不同 requestId。
