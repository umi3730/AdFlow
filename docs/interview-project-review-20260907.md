## 定位

AdFlow 更适合定位为「广告决策与事件计量后端，包含并发准入、预算频控、幂等事件和性能优化」，架构为模块化单体。对于校招/初级 Go 后端，可以作为讲深的主项目；若用于有经验的分布式岗位，还需要多实例故障测试和长期运行证据。

## 优势

1. 业务约束能自然引出后端难点：同一请求重复到达、预算预占与确认、每用户频控、曝光前置、重复消息、重启恢复。
2. 有失败驱动优化记录：候选 N+1、Kafka 串行/逐条持久化、候选快照、画像 Cache-Aside，而不只是中间件依赖清单。历史基线与原始汇总见 `performance-baseline.md` 和 `work/k6-*.json`。
3. 有明确实现边界：每进程并发门控与共享 Redis 限流分开；Kafka 至少一次配合 eventId 去重；候选配置缓存不缓存用户预算；Agent 输出经过校验、人工确认和权限检查。
4. 有可运行演示、初始化与删除规则、Go 测试、集成测试脚本和前端回归。演示方便解释业务；测试数量不能代替错误场景覆盖。

## 短板及可追问点

- **广告分配仍简单。** `internal/decision/application/service.go` 按 campaign ID 排序，返回第一个满足规则、频控和预算的候选，素材按 requestId 哈希选择。可以称确定性规则决策；不能称竞价/eCPM 优化、个性化推荐或预算平滑投放。多个计划覆盖同一人群时，靠前计划可能长期占先。
- **超过 100 条候选有正确性缺口。** `internal/decision/adapter/campaign/provider.go` 只读取一页 `Limit: 100`，未继续分页。应该先修这个，再增加负载规模。
- **多实例一致性仍需证明。** 画像缓存的 `keyLocks` 和 miss 合并均是进程内机制。两个 API 实例的数据库写与缓存回填可能交错，不能把单进程防旧值覆盖宣传成跨实例保证。需要受控交错测试，再决定版本号/CAS 或其他一致性方案。
- **审计是尽力写入。** 审计中间件在业务响应后单独记录，失败只记日志；不能宣称业务变更与审计原子落库。是否升级为事务/Outbox 耦合，取决于业务要求。
- **性能证据有环境边界。** 历史数据涉及 Windows API/k6 与 WSL 中间件；目标到达率不是整场平均吞吐。冷热缓存对比也不等于两版代码的 A/B 收益。现有结果可以讲优化过程，尚不足以证明生产容量。
- **真实依赖回归未成为自动门禁。** 默认 Go CI 不带 integration build tag；新 MySQL 演示初始化目前主要是 sqlmock。应补临时真实依赖环境，自动验证事务、迁移与重启。
- **交付留档尚不完整。** 一部分工作未提交，原始性能汇总在被 Git 忽略的 work 中；独立机器复现和版本对应关系还需要整理。
- **业务闭环还有小缺口。** 普通计划到期状态、画像未保存即调试、总览逐计划读取统计的问题见 `feature-review-20260907.md`。

## 建议顺序与验收标准

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 修候选分页、过期计划展示和未保存画像跳转 | 101/200 条候选不遗漏；冻结时钟覆盖日期边界；输入不被无提示丢弃 |
| 2 | 建立真实依赖的可复现回归入口 | 干净机器按文档启动；自动迁移；真实 MySQL/Redis/Kafka 测试可运行；报告绑定代码版本 |
| 3 | 做一次严格性能 A/B | 同机同数据同配置；明确冷/热阶段；多次重复；保存吞吐、分位数、错误、CPU/内存/分配、连接池和消息积压 |
| 4 | 多实例一致性与故障恢复 | 两个 API 实例写同一画像、冷缓存回填、Redis 中断、重复消息、消费重启均有断言；记录恢复后最终状态 |
| 5 | 加深广告选择策略 | 增加明确的优先级/权重公平性策略，验证同人群多计划的分配比例；之后再考虑 pacing |
| 6 | 增强诊断 | 将已有 Prometheus 指标组织成看板，结合 pprof；确有定位需要时增加 OpenTelemetry tracing |

不建议为了简历立即拆微服务、堆 Kubernetes/Elasticsearch 或扩大 Agent 编排。优先把已有预算、缓存、Outbox 机制讲清楚并拿出故障与优化证据。

## 面试准备

- 同一个 requestId 并发到达，预算和频控如何保证不重复占用？
- Outbox 已写入但 Redis 确认失败，或者 Kafka 已收到但 Outbox 未更新，会如何恢复？
- 消费处理成功但 offset 未提交，重放为什么不重复累计？
- 候选缓存五秒内暂停计划的行为是什么，为什么接受这一取舍？
- 两个实例同时更新同一画像，当前保证是什么、缺口是什么？
- 性能提升来自减少查询、减少网络往返还是批处理？怎样用同条件测试证明？

能结合代码和实验回答这些问题，比单纯展示「100 并发」更能说明后端能力。
