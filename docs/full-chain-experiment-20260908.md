# HTTP 到统计落库的全链路对照

## 结论

2026-09-08 北京时间 10:39:31～10:45:48，使用当前真实 API 二进制，在隔离环境完成两种队列背景、三轮配对、两种索引模式的全链路测试。

**1440 条正式业务流程全部成功。**连同 36 条预热，共 1476 次曝光结算、4428 条事件受理/发布/消费；逐组核对预算、频控和统计，并验证重复提交不增加计数。

索引对全链路的收益依赖队列情况：

| 场景 | 索引不可见：全链路完成 P95 | 索引可见：全链路完成 P95 |
| --- | ---: | ---: |
| 百万条历史 Outbox 均标记已发布，没有背景待结算记录 | 1280.65ms | 1300.15ms |
| 同一历史夹具中约 5 万条静态滞留 SETTLING 记录 | 17822.43ms | 1288.20ms |

每格合并三轮的 **360 个正式样本重新计算分位数**，不是平均三个 P95。正常队列没有观察到有意义的全链路提速；滞留压力下索引避免了大量重复扫描，显著降低新请求等待时间。不能把 SQL 微基准的收益直接推广到所有业务场景。

## 实际走过的链路

1. 登录获取 JWT，创建计划、素材及已保存用户。
2. 普通 `/v1/decisions` 读取画像，执行定向、同广告位三家广告主一价竞价，检查和预占预算/频控，持久化决策。
3. 通过 `/v1/events` 顺序回传曝光、点击、转化，每条新事件应返回 202；HTTP 入口执行真实数据库事务提交。
4. 结算 worker 原子确认 Redis 预算和频控，写入 MySQL SETTLED 状态，并释放 Outbox 待投递事件。
5. Outbox relay 向真实 Kafka 投递；消费者验证结算、执行事件幂等去重，并在同一事务更新统计。
6. 并行观察器确认三个 `processed_events` 行均已提交；随后核对统计、结算、发布状态、Redis 账目和 Kafka lag。

本次使用已有画像查询，**不是绕过画像数据库/缓存读取的临时用户模拟接口**；每轮都应命中最高出价广告，不把 No-Ad 作为成功流量混入测量。

## 环境与控制变量

- CPU：Intel Core i7-8700；Linux/WSL2，MySQL 8.0.46，buffer pool 128 MiB，Go 1.27.0。
- 测试客户端、独立 API 和 MySQL 位于同一 WSL；HTTP 为 loopback，MySQL 为 Unix socket。API 使用当前统一连接配置，真实提交，并未回滚测量请求。
- MySQL、Kafka 与原项目共享本机资源，但测试使用新数据库和专用 Kafka Topic/消费组。Redis 使用独占的临时进程及端口，不清空业务 Redis。
- 开启 JWT、MySQL 审计、画像缓存、Redis 滑动窗口准入、预算/频控和 Kafka。禁用内置样例，Agent 使用 mock 且不调用。
- 每组创建 3 个广告主的计划，出价 2/3/5 分，定向相同；日预算充足，频控上限 100，每个用户只测一次。所有请求都应由 5 分计划中标。
- 画像在正式测试前经 HTTP 预热，另执行并排空 3 次完整预热流程。正式每组 120 请求，目标 10 轮/秒，最多 20 个客户端在途流程，达到限额后等待而不是无限堆积。
- 每个场景三轮配对，模式顺序 AB、BA、AB。仅切换 `(aggregate_key,status)` 的可见性，不改变 API 代码、worker、超时、限流或连接池。
- 两种模式均保留物理索引及其维护成本；不可见对照仍使用原有状态索引，不是没有任何索引。
- 每组创建独立计划、用户、请求 ID，前组的已完成数据保留。正式新增事件共 4428 条，相对百万历史夹具不到 0.5%；并非每组重置为逐字节相同数据库快照。

**历史夹具的限制：**`hist-` 前缀数据只模拟 Outbox 的体量和状态分布，并未真的执行百万次投放。在健康背景中标记 PUBLISHED；压力场景把约 5% 改成 SETTLING，但不建立对应结算任务，以维持静态扫描压力。这是故意构造的滞留场景，不冒充健康生产队列，也不把这批夹具纳入本次核账或要求其排空。

## 耗时口径

| 字段 | 含义 |
| --- | --- |
| decisionMs | 决策请求发送至完整读回响应 |
| allEventsAcceptedMs | 决策开始至曝光、点击、转化的 HTTP 请求均受理，包含入口真实事务提交 |
| committedObservedMs | 决策开始至并行观察器首次查到三个已提交的消费记录；消费记录和统计更新在同一事务中 |
| allEventsProcessedMs | 诊断用：最后一条消费记录中的 processed_at 减去客户端开始时间；记录时间在事务提交前赋值，不能当作精确提交耗时 |

本文“全链路完成”使用 **committedObservedMs**，包含观察器 100ms 轮询间隔与查询/调度开销，是观测到完成的时间上界。观察器与派发并行，避免把“等待全组请求派完”错误计入前面请求的延迟。各时间来自同一 WSL 主机的 UTC 时钟。

## 正确性核验

每组 120 正式 + 3 预热：

- 123 次结算为 SETTLED。
- 369 条事件回执、369 条 PUBLISHED Outbox、369 条 processed_events。
- 获胜计划：曝光、点击、转化各 123；转化价值 61,500 分。
- Redis 预算扣费 615 分、预占余额 0；123 位独立用户各有一次频控记录。
- 其他广告主没有获得统计。
- 重复提交一份决策及其三类相同事件，事件返回 200 且 recorded=false；最终账目仍为上述数值。
- 保存一条请求联查快照，三分区 Kafka lag 快照均为 0；本组 Outbox 无非 PUBLISHED 状态。

12 组合计：1476 次结算、4428 条消费事件、模拟预算扣费 7380 分，全部核验通过。1440 条正式样本无 HTTP 失败，全部观察到统计事务提交。重复调用用于正确性核验，不混入正式延迟样本，也不增加事件数。

## 新发现与后续方向

正常背景下，事件受理约百毫秒，而统计提交可见约一秒。当前 Outbox relay 每 500ms 轮询一次；点击/转化需要等曝光发布之后才能领取，可能落入下一轮轮询。

原始请求示例中，曝光发布记录时间为 `02:40:42.072Z`，点击/转化为 `02:40:42.572Z`，间隔约 500ms。这与代码的轮询/依赖顺序相符，但不是对全部延迟的严格归因实验。

下一步可单独验证“有任务时连续处理、空闲时等待”的 relay 调度策略，保留曝光先行和消费者幂等约束。此次没有混入该改动，否则无法隔离索引收益。

## 结果适用范围

全链路结果对应以下受控条件：

> 在百万条 Outbox 背景记录、约 5 万条静态待结算积压的隔离场景下，以 10 轮/秒执行三轮索引对照，将广告决策至三类事件统计提交可见的 P95 从 17.82s 降至 1.29s；全套 1440 条正式流程均完成，并核对预算扣减与事件幂等。

结果边界：正常队列下约 1.3s，没有观察到明显提速；该指标含 100ms 轮询观测误差，压力背景为合成夹具，不是生产故障恢复或最大容量数据。单 SQL 与完整链路实验的负载和计时范围不同，不能混用结论。
