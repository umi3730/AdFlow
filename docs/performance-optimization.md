# 性能分析与优化方法

当前可用工具包括按实例启用的 pprof、数据库连接池统计、k6 完整链路与过载保护验证。工具操作见 [pprof 指南](profiling.md)，最新数据见 [连接池对照实验](mysql-pool-comparison-20260908.md)。

## 已得到的结论

九组交叉测试中，最大连接数 30/60/100 都通过最终核账；扩大连接数消除了短暂等待，但没有观察到完成吞吐或统计延迟的稳定改善。默认保留 30/10，不把修改配置本身当作优化收益。

## 分析顺序

1. 确认被测 API 地址、PID 和版本，区分请求受理与异步完成。
2. 固定数据、请求分布、缓存预热与非目标参数，交叉改变一个参数。
3. 同时记录成功、拒绝、非预期错误、延迟和积压，再核对最终事件与金额。
4. 对累计 DBStats 使用窗口差值。连接等待次数包含后台连接获取，不是等待过的 HTTP 请求数量。
5. CPU、堆和阻塞采样各有不同含义；CPU profile 不能直接衡量 SQL 提交的等待时间。
6. 按证据决定是否修改默认值，保存不利结果和运行边界。

## 下一步候选

- 在最大连接数固定的前提下，比较空闲连接数 10/20，检查连接反复创建和关闭是否减少，以及端到端指标是否改善。
- 对同步审计、事务提交和结算 SQL 做独立耗时测量与对照。
- 只有分配证据显示必要时，再考虑接入对象池；未使用的 pool.go 已在工程审查中移除，重新引入前须证明对象生命周期和分配收益。
