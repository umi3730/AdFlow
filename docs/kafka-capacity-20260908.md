# Kafka 全链路压测：吞吐边界与恢复缺陷

最新长测：修复后 45 轮/秒通过三组各 120 秒和队列趋势检查；50 轮/秒第三组仍出现积压增长，见 [容量续测](kafka-capacity-followup-20260908.md)。

后续：本页发现的恢复问题已修复，真实死锁/接管回归和三轮 50 轮/秒 Kafka 测试通过，见 [结算恢复修复](settlement-recovery-fix-20260908.md)。下文保留修复前事实，不能当作修复后的当前状态。

## 最终结论

本轮确实跑通了“决策 → 曝光/点击/转化 → Redis 结算 → Outbox → Kafka → 统计落库”，但补充复测暴露了**MySQL 死锁后的结算恢复缺陷**。因此目前不能给出可靠的 Kafka 全链路稳定 QPS 结论，也不能只引用前面通过的轮次。

初次探索中，60 轮业务/秒在三轮各 60 秒测试里满足有限窗口的延迟及排空标准，但未处理事件有增长趋势。随后单独验证 50 轮/秒时，HTTP 全部成功，后台却发生死锁，3 条曝光进入 RECONCILE。本次主要价值是发现了这个“接口成功、异步链路未完成”的真实问题。

一轮业务为 1 次决策 + 曝光/点击/转化各 1 次回传。因此：

- 60 轮/秒约对应 240 个业务 HTTP 请求/秒、180 条事件/秒。
- 50 轮/秒约对应 200 个业务 HTTP 请求/秒、150 条事件/秒。

这与此前单独决策接口 450 QPS 的口径不同，不能直接比较为 Kafka 加速或减速倍数。

## 实验设置

- k6 v2.2.0 固定到达率，真实 API、MySQL、Redis、Kafka；客户端与依赖共处本机 WSL。
- 新建隔离数据库、独占 Redis、专用 Kafka Topic/消费组；Kafka 三分区、单副本。业务环境未改动。
- 1000 个已保存用户，3 个广告主出价 2/3/5 分，全部满足定向，必须命中 5 分计划。
- 每阶段新计划、新请求前缀；保留已有阶段数据。预算/频控/幂等保持开启，不在压测中途重置资金状态。
- 每阶段 3 次完整预热流程不计入正式速率和延迟，但计入计划预算/统计。
- 每 250ms 观察当前阶段消费记录；三个事件全部已提交时记录从决策开始到统计提交可见的延迟，含轮询/查询/调度开销。
- 每秒采集事件受理、结算、发布及消费数量；结束后核对金额、事件数、重复回传和 Kafka broker offset。

预定有限窗口标准为：决策 P95 < 300ms，整轮 HTTP 受理 P95 < 1000ms，统计提交可见 P95 < 5000ms，业务错误率 < 0.1%，无未派发迭代，无 No-Ad，10 秒内排空且账目正确。达到这些有限窗口条件并不证明无限时长的队列稳定性。

### 采样工具问题

65 轮/s 长测的 3901 次业务全部计量完成，金额/偏移正确，但完成时间只记录了 3862 次。原因是最终一次时间查询与随后计数查询之间又有批次提交；程序见总数已齐就退出，漏掉最后 39 个观测时间。

已修正为计数证明完成后再补一次观测，并增加确定性交错的 sqlmock 回归。旧时间没有补造，该阶段不用于完整分位数结论。三轮 60 轮/s 的观测数量均完整，仍保留其有限窗口数据和积压警示。

## 50 轮/s 补充复测发现真实缺陷

使用修正后的观察器，在全新的隔离环境尝试三轮各 60 秒确认；第一轮即失败，停止继续加压。

- 决策 3001 次，全部命中；曝光、点击、转化共 9003 次回传全部被 HTTP 接收。
- 决策 P95 60.88ms，整轮受理 P95 177ms，客户端错误率和 dropped iterations 均为 0。
- 后台出现 MySQL 1213 死锁，随后有 3 条曝光进入 RECONCILE，完整账目核验失败。
- 此时 Kafka broker 各分区 lag 都为 0，但上游尚有无法发布的事件，证明 **lag=0 不能替代完整链路核账**。

关键日志（北京时间）：

```text
13:25:22.348 settlement worker iteration failed
  Error 1213 (40001): Deadlock found when trying to get lock

13:25:52.440 / .448 / .456
  impression requires settlement reconciliation
```

三条 RECONCILE 请求尾号为 1755、1757、1758。早先核账快照只看到第一条 RECONCILE、其他任务尚在处理，日志随后记录三条；这些不是同一时刻的状态，不能混为最终原子快照。

含预热应有 9012 条 Kafka 事件，而 broker 最终偏移合计为 9003。结合上游 RECONCILE 与受理记录，问题发生在结算/发布前，不应描述为 Kafka 消费丢消息。测试已结束并清理隔离数据，原始日志与快照保留用于回归设计。

## 已保存的死锁证据与代码链条

`SHOW ENGINE INNODB STATUS` 捕捉到两个事务在同一隔离库的 `event_outbox` 上形成索引锁循环：

| 事务 | 操作 | 已持有 | 等待 |
| --- | --- | --- | --- |
| 1 | 结算完成，将请求事件 SETTLING → PENDING | idx_outbox_request_status | idx_event_outbox_claim 的插入意向间隙锁 |
| 2 | 转发器批量领取，将事件改为 PROCESSING | idx_event_outbox_claim | idx_outbox_request_status 的插入意向间隙锁 |

MySQL 选择回滚事务 1。已有联合索引和 SKIP LOCKED 并没有排除所有状态变更时的死锁。

代码与时间记录支持以下恢复链条：

1. Settlement worker 一次领取最多 10 个任务，租约 30 秒。
2. 已领取批次中，一次 `CompleteSettlement` 遇到错误会直接从 `RunOnce` 返回。
3. 后续尚未处理的已领取任务保留租约，不能立即被下一轮接管。
4. Redis 决策预占本身也是 30 秒。等任务租约到期时，部分尚未确认的预占已过期。
5. 恢复处理无法证明结算，转入 RECONCILE；对应事件不能继续正常发布。

死锁报告、约 30 秒的日志间隔以及未处理请求的创建时间相互吻合。这里不将 RECONCILE 描述为“错误扣费”：系统拒绝把无法确认的结算当成成功，但自动恢复路径未完成业务闭环。

## 下一步修复范围（尚未实施）

- 针对死锁回滚的事务建立有界重试，确认重试单位、退避和幂等边界。
- 批处理提前退出时妥善释放或重新调度尚未执行的任务，避免被整个 30 秒租约拖住。
- 评估结算更新与转发领取的隔离级别、锁顺序及状态索引变更，不能只删除索引或扩大超时掩盖问题。
- 用受控交错/故障注入重现这一链条，断言所有受理事件最终完成且不重复扣费，再复跑 Kafka 负载。

当前 relay 每 500ms 最多取 100 条事件，名义转发上限约 200 条/s，即三事件完整业务约 66.7 轮/s；实际执行和依赖等待还会降低这一值。这也是吞吐优化候选，但应先解决恢复正确性，不把调大批次混入本次结果。
