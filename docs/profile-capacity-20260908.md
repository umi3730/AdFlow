# 用户画像 GET：本机稳定 QPS 探索

## 可报告的结论

被测接口为 `GET /v1/profiles/{userId}`，Redis 热缓存、正常 JWT 鉴权、1000 个已保存用户。不是广告决策接口，也不是整个项目的吞吐上限。

在预先定义的 **P95 < 100ms、业务错误率 < 0.1%、dropped_iterations=0** 标准下，本次最高完成三轮各 60 秒确认的测试档位为 **1000 QPS**。

| 目标速率 | 验证结果 |
| --- | --- |
| 1000 QPS | 三轮各 60s 全部通过，P95 为 5.83 / 2.01 / 1.67ms |
| 1500 QPS | 20s 短测和首轮 60s 通过；第二轮 60s 的 P95=105.38ms，24 次未派发，未稳定通过 |
| 2000 QPS | 20s 实际约 1958.56 请求/s，P95=265.20ms，483 次未派发，不符合本次标准 |

**1000 是本次已验证的稳定目标档位，不是已证明的绝对最大值。**搜索分辨率为 500 QPS，1000～1500 之间没有细分；更高目标的失败也不能单独证明瓶颈一定属于后端，因为发压器与服务端共享主机。

本次实际发出并完成 459,500 个画像请求，响应与内容错误率均为 0。但在两个失败阶段另有 507 个计划迭代未派发，因此不能只根据“实际请求错误率 0%”判定容量达标。

## 为什么与此前 JMeter 约 2000 请求/s 不同

此前 JMeter 使用固定 20 线程、每组 15 秒的闭环模型：收到响应后才继续发下一次请求。本次 k6 按固定到达率持续尝试发出请求，并要求较长复测中没有丢弃迭代。

负载模型、发压器、连接数量及持续时间不同，结果不能直接互换。两者分别证明各自条件下的表现；不能据此宣布性能从 2000 降到 1000，也不能用 JMeter 的短测覆盖本次失败记录。

## 实验设计

- 单机 WSL2，Intel Core i7-8700，12 个逻辑 CPU；API、k6、Redis、MySQL 共享资源。
- 使用当前生产 API 二进制，保留 JWT、日志、JSON 编解码、Redis 缓存及现有配置。没有为了结果关闭日志或修改超时、连接池。
- MySQL 8.0.46，buffer pool 128 MiB；MySQL 走 Unix socket，HTTP/Redis 走 loopback。画像使用 `mysql-redis`。
- 所有测试数据库、API 和 Redis 均独立创建；没有修改业务库、业务 Redis 或已有 API。
- 每阶段仅清空独占 Redis，重新读取全部 1000 个用户预热，避免缓存五分钟过期造成冷热混杂。正式阶段记录到的用户表读取增量均为 0。
- k6 v2.2.0，固定到达率，每轮预分配 256 VU，最大 512 VU。请求超时 2 秒，每次校验状态码、userId、score。
- 初始阶梯计划为 500/1000/2000/4000/8000/16000 QPS，各 20 秒，首个失败后停止翻倍；本次实际只测到 2000，后面的档位没有执行。
- 按 500 QPS 分辨率缩小区间，再执行候选速率的三轮各 60 秒确认；1500 长测失败后回退到 1000。
- 轮次之间存在重新预热及 k6 初始化，不将三次 60 秒写作毫无间隔的连续三分钟压测。

## 完整阶段结果

| 阶段 | 目标 QPS | 时长 | 实际平均 HTTP QPS | P95 ms | P99 ms | 未派发 | 达标 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 初测 | 500 | 20s | 499.97 | 1.82 | 5.84 | 0 | 是 |
| 初测 | 1000 | 20s | 999.90 | 1.81 | 5.66 | 0 | 是 |
| 初测 | 2000 | 20s | 1958.56 | 265.20 | 280.06 | 483 | 否 |
| 区间探测 | 1500 | 20s | 1499.91 | 16.61 | 67.09 | 0 | 是 |
| 持续确认 1 | 1500 | 60s | 1499.75 | 9.45 | 81.50 | 0 | 是 |
| 持续确认 2 | 1500 | 60s | 1499.54 | 105.38 | 159.69 | 24 | 否 |
| 回退确认 1 | 1000 | 60s | 999.99 | 5.83 | 68.80 | 0 | 是 |
| 回退确认 2 | 1000 | 60s | 999.95 | 2.01 | 35.16 | 0 | 是 |
| 回退确认 3 | 1000 | 60s | 999.97 | 1.67 | 10.16 | 0 | 是 |

以上各阶段已返回请求的 HTTP/内容错误率均为 0，失败原因是尾延迟和未派发迭代，而不是 HTTP 500。`dropped_iterations` 指发压器没有启动的计划迭代，不等于服务器丢弃已经收到的请求。

三轮 1000 QPS 长测累计完成 180,002 次请求。实际请求数以 k6 Counter 为准，不强行等同于目标速率乘时长的整数理论值。

## goroutine 与资源观测

每秒采集 `/proc` 的 API、k6、Redis、MySQL 进程 CPU/RSS/线程数，及 API 的 `go_goroutines`、`GOMAXPROCS`。每秒一次 metrics 请求属于额外观察流量，不进入 k6 QPS。

2000 QPS 失败阶段：

- 整机 CPU 采样最高约 24.38%，未观察到所有 CPU 核心耗尽。
- API 平均 CPU 约 79.50%，k6 约 92.15%，Redis 约 10.25%；这些百分比以单个逻辑核为 100%，不是占整台机器同样比例。
- API goroutine 采样最高 **1034**。
- 正式请求仍命中 Redis，用户表读取增量为 0。

这些数据不足以把瓶颈精确归因为 CPU、Redis、日志 I/O 或某把锁。日志写在工作区卷，发压器和服务共机，连接数也随负载变化，都是待单独控制的因素；本次没有进行 CPU/阻塞剖析来证明某个根因。

goroutine 超过 256 与现有配置并不矛盾：256 是广告决策执行门控，此次画像 GET 不经过该门控；goroutine 总数还包括连接、运行时和后台任务。这里记录的是每秒采样峰值，不是全程绝对峰值。

## 结果适用范围

针对用户画像查询，使用 k6 固定到达率逐级施压，预先约定 P95 小于 100ms、错误率低于 0.1% 且没有未派发迭代。1500 QPS 虽然短测通过，但持续复测失败，因此没有直接作为容量结论。回退到 1000 QPS 后，三轮各一分钟全部通过。同时记录 goroutine、进程资源和缓存命中，保留失败阶段；这证明的是本机当前部署条件下的稳定档位，不是整个系统或生产环境的最大 QPS。

若要继续缩小上限，需要细测 1000～1500 区间、延长稳态、使用独立发压机，并对日志与阻塞情况做归因。不能通过临时放宽验收线或只保留最好的一轮来改变容量结论。
